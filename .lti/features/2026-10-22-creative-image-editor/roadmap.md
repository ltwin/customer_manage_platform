# Roadmap

## 子项

串行推进（policy: serial）：前一项归档并合回之后，下一项才进入实施；后面的子项可以提前准备设计。

顺序原则：
- **先消除不确定性**：I0 回答「60MP 多图层能不能在浏览器里流畅编辑，像素怎么存、怎么保存」。结论经 Epic 修订回填 design 和 contracts，再开始 I1。
- **再做最小贯通**：I1 做到「新建或从图片打开 → 分层编辑 → 保存与历史 → 导出回画布」走通，后面的能力都长在这条链路上。
- **然后补齐基础**：I2–I4 补上选区与蒙版、画笔、调整图层。几乎所有精修和合成操作都依赖这三样。
- **助手提前接入**：I5 搭好助手的读取、参数化操作和代码作画。之后每个能力子项同时交付助手对应的操作，和 3D 场景的做法一样（C3 之后的子项各自扩展助手工具）。
- **再扩展能力**：I6–I13 先做精修和合成的主力工具，再做 AI 能力，最后做文字和图层样式。

**I0 穿刺清单**：

1. **分块存储与保存**：
   - 分块尺寸、编码（精确无损、不经 Canvas2D 预乘）和在 Worker 里的编解码耗时。
   - 上传方式与批量；60MP 原片首次分块上传的耗时。
   - 一笔画完后增量保存的数据量和耗时。
   - 内容哈希去重在历史修订之间的效果。
2. **GPU 合成**：
   - 分块驻留、按缩放级别的 mip、视口内合成。
   - 27 种混合模式、混合颜色带与调整图层的着色写法，比较 TSL（含 compute）和直接写 WGSL compute。
   - 是否必须 WebGPU；WebGL2 后端能否支撑。
   - 设备丢失后的恢复。
3. **画笔与重计算**：
   - 画笔笔触在 60MP 图层上的延迟。
   - 大半径高斯模糊。
   - 液化位移场的原型。
4. **大图端到端**：
   - 60MP、10 层以上文档的打开、浏览、属性拖动、保存、整图导出（PNG / JPEG / WebP 的文件大小与媒体上限的冲突）。
   - 浏览器内存峰值。
5. **对照组**：
   - PhotoCraft 的引擎 crate 编译成 WASM，在同一基准下测包体积、内存、合成与画笔性能。
   - 只调用它的引擎、不用它界面的可行性。
6. **一致性基线**：用 Photoshop 生成参考图，定误差阈值（需要 owner 协助出图）。覆盖：
   - 27 种混合模式；
   - 混合颜色带；
   - 首批调整；
   - 加深 / 减淡在三种范围下的响应（对灰阶渐变做固定参数处理）。
7. **浏览器保留快捷键**：在 Chrome / Edge / Safari 上实测 `Cmd/Ctrl+Shift+N`、`Cmd/Ctrl+T`、`Cmd/Ctrl+W`、`Cmd/Ctrl+N` 能否被页面接住：
   - 普通标签页；
   - 浏览器全屏 + Keyboard Lock；
   - 安装成应用（PWA 窗口）。
8. **浏览器端分割预研**（不阻塞 I1）：SAM 2.1 / SlimSAM 的 ONNX 在 WebGPU 上的编码耗时和模型体积。

### 验收责任

- 每个子项按自己的 proposal 验收，由 owner 接受后归档。
- 只能由 owner 判断的质量验收：
  - I5：助手作画样例。
  - I10：智能选区在真实原片上的质量。
  - I11：生成式填充的接缝。
  - Epic 整体验收的 AC-11：两张端到端样张。
  - 技术检查通过不等于质量通过。
- Epic 整体验收按 proposal 的 11 条 WHEN/THEN，在 I13 归档后进行。

### 后续（不在本 Epic）

### 与其他 Epic 的关系

- **`scene-editor-3d`**：
  - I5 需要把场景专用的客户端任务（`data: 场景客户端任务`）推广为通用文档可用的机制，开工前与该 Epic 协调契约归属。
  - I1 需要把场景专用的导出图来源（`data: 导出图来源`）推广到图像文档。
- **`scene-webgpu-renderer`**：
  - 如果 I0 决定图像合成沿用 three.js `WebGPURenderer` + TSL，就和场景共用渲染器创建入口与 `patterns: 场景着色写法` 的约束，届时修订该模式的适用范围。
  - 两个 Epic 都是串行策略，只约束各自的子项；跨 Epic 同时实施时，由宿主隔离工作区，合回时重新验证。
