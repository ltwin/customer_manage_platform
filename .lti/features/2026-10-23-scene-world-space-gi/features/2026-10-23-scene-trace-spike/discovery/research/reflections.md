# 组 4：反射补追

> 2026-10-24，S0 任务 3.3。结论：**可行**。
> - **补追的效果**：fork `SSRNode`，沿 SSR 自己的 GGX 采样方向，对没命中的采样和边缘淡出带补追。
>   - `mirror-board` 的镜面柜里映出了摄像机背后的物件；
>   - 物件离开画面时，地板上的倒影保持不变，只有 SSR 时会跳变约 12%。
> - **两个位置**：A（片元里补追）和 B（compute 里补追）出图相同（平均差 ≤ 0.004 级），A 每帧便宜 0.3–0.8 ms。**推荐 A**。
> - **U3 的 `r_max`**：建议视口取 0.5，导出取 1.0。
> - **途中发现的四个问题**，都与 S1 直接相关，见「顺带发现」：
>   - three 的 GGX 采样在正对摄像机的表面上产生 NaN 方向，产品现在的 SSR 也受影响；
>   - TSL 在 `Switch` 各分支间共享的表达式会读到未赋值的变量；
>   - 网格有多个 group 时，每个 group 是顶层的一项；
>   - three 的时间戳在嵌套 pass 里归属不准。

## 做法

原型在 `prototype/spike/trace/`（S0 期间在 `frontend/` 下，运行方法见 `prototype/README.md`）：fork 是 `SSRTraceNode.js`，命中点着色是 `hitShade.ts`，用例是 `reflections.ts`。测量脚本是 `measure/reflections.mjs`，数据和图在 `reflections/`。

- **管线**：用产品自己的预通道和拆分光照 pass（`render/giSplit.ts`），按 `realtimeGI.ts` 的合成公式拼出反射项：
  - SSR 命中的地方，用反射替换材质的环境高光 `envSpec`；
  - 没命中（`cover = 0`）的地方，保留 `envSpec`。

  时域重投影和降噪不变，这里都去掉了。每张图取 SSR 64 帧的平均（噪声每帧前进），所以图与图之间的差别只来自补追本身。
- **fork 的改动**（`SSRTraceNode.js`，基于 three 0.186.1，文件头注明了上游版本，改动处都标了「fork:」）：
  - 两类采样会记下一条补追请求（世界空间方向、份额），以及它的 GGX 权重：
    - 屏幕空间没命中的采样，份额为 1；
    - 边缘淡出带里命中的采样，份额为 1 − 边缘因子。
  - 只补追粗糙度低于 `rMax` 的像素。
  - SSR 把淡出带向环境混合，这里的环境是 0（产品没有给 SSR 环境），所以「SSR 结果加上补追份额」就等于 `mix(补追, 命中, 边缘因子)`。
  - **A**：片元着色器的末尾直接求交、着色，按与原输出相同的亮度上限和强度加进去。
  - **B**：渲染目标多两张同名纹理（`ray`、`weight`），片元以 MRT 输出补追请求；一个 compute pass 读取请求，追踪、着色后加进反射的一份拷贝（存储纹理）。之后的节点读这份拷贝。
- **命中点着色**（`hitShade.ts`）：沿用组 3 的材质表、14 个预设和物理光照，有两处不同：
  - **宽度**：由光线锥合成光线微分。锥在像素处的宽度等于像素角乘以视距，之后每米加宽「像素角 + 2 × 粗糙度²」；落到表面时，沿光线方向按 1/cosθ 拉长。
  - **太阳阴影**：朝太阳发阴影光线，理由见组 3 的 `hit-shading.md`。
- **打包**：`TraceLayer`（组 2，一个实例一项）。参考场景很小，BVH 直接在主线程上用 SAH 构建。
- **场景**：
  - `mirror-board`：镜面柜和光滑地板，摄像机背后有方块和圆柱；
  - `backlit-room`、`materials`：粗糙表面多；
  - `cornell`：封闭的盒子，补追光线全部命中。
- **测量**：
  - **出图对照**：A 与 B 之差，A 与只有 SSR 之差；
  - **俯仰序列**：`mirror-board` 的摄像机逐步下压，金属球从画面上沿移出，它在地板上的倒影仍在画面里。在球心关于地面的镜像点、从摄像机看去落在地板上的位置，测 11 × 11 像素的平均亮度；
  - **帧时间**：每帧从提交到 GPU 完成的墙钟时间，三种做法交替各 30 帧，取中位数；
  - **补追数量**：按粗糙度分段统计，`rMax = 1`；
  - **存储缓冲上限**：各阶段在 core 和 compatibility 两种功能级别下的上限。

## 结果

### 补追让屏幕外的东西出现在反射里

- **`mirror-board`**（`mirror-board-ssr.jpg` 对 `mirror-board-A.jpg`）：
  - 只有 SSR 时，镜面柜里只是一片灰：环境高光，没有物件；
  - 补追后，映出摄像机背后的红、绿、黄方块和白色地板；
  - 整图平均差 10.8 级。
- **其他场景**：补追带来的差异分别是 `backlit-room` 1.7 级、`materials` 0.7 级、`cornell` 2.0 级，主要来自粗糙表面上屏幕外的环境光照。

### 接缝（俯仰序列，`mirror-board-pitchStrip.jpg`：上排只有 SSR，下排 A；品红十字是测量点）

| 下压角度 | 球在画面里 | 只有 SSR | A |
|---|---|---|---|
| 6°–24° | 是 | 0.6816 | 0.6816 |
| 30° | 刚到上沿 | **0.7619**（+11.8%） | 0.6851（+0.5%） |
| 36° | 已离开 | **0.7615** | 0.6851 |

- 只有 SSR 时，球一到屏幕上沿，它的倒影就变成环境里亮白的天空和灯光（图中下排看得到倒影，上排在同一位置是一团亮白）。
- A 的倒影始终是球，变化 0.5%：这个差异来自补追命中点的着色（不做凹凸），而不是屏幕边缘的接缝。
- 边缘淡出带也没有变暗：下压 30° 时，球正处在屏幕上沿的淡出带里，A 仍只差 0.5%，淡出的份额由补追补上了。

### A 与 B

| 场景 | A 与 B 的平均差 | 超过 2 级的像素 |
|---|---|---|
| `mirror-board` | 0.004 | 0.04% |
| `backlit-room` | 0.001 | 0 |
| `materials` | 0 | 0 |
| `cornell` | 0.001 | 0 |

两种位置出图相同。`mirror-board` 那 0.04% 的像素，很可能是因为 B 把方向和权重存成了半精度：方向误差约千分之一弧度，镜面上看得出来。这一点没能验证：把 `ray` 和 `weight` 目标改成 32 位浮点，就和半精度的输出目标混成了不同格式的 MRT，本机试下来不可用。

### 帧时间（1536 × 1024，预通道 + 拆分光照 + SSR，墙钟中位数，单位 ms）

| 场景 | 只有 SSR | A，`r_max` 1 | B，`r_max` 1 | A，`r_max` 0.5 | B，`r_max` 0.5 |
|---|---|---|---|---|---|
| `mirror-board` | 1.8 | 2.7（+0.9） | 3.0（+1.2） | 2.7 | 3.0 |
| `backlit-room` | 3.4 | 7.9（+4.5） | 8.7（+5.3） | 3.4（+0.1） | 3.6 |
| `materials` | 3.0 | 5.1（+2.1） | 5.8（+2.8） | 3.2（+0.2） | 3.4 |
| `cornell` | 3.6 | 9.6（+6.0） | 10.1（+6.5） | 3.8（+0.4） | 4.1 |

- **B 比 A 贵 0.3–0.8 ms**：多两张全分辨率的 MRT 目标（每像素 16 B）、一张拷贝，还多一个 pass。
- **耗时拆分**（`cornell`，`r_max` 1，A，补追约 82 万条，几乎全部命中）：

  | 内容 | 比只有 SSR 多出 |
  |---|---|
  | 只遍历，不着色 | 2.1 ms |
  | 加上材质求值和光照，不发阴影光线 | 3.4 ms |
  | 加上阴影光线（完整） | 6.0 ms |

  遍历约占三分之一，着色约占四分之一，阴影光线约占四成。
- **首帧**（含编译，内联了 14 个预设）：A 0.4–1.3 s，B 0.4–1.2 s。
- **压力场景**：这里没测（参考场景的 BVH 在主线程上建）。按组 2 的反射光线吞吐（每毫秒约 7.4 万条）和阴影光线吞吐（每毫秒 18.5 万条）估算，30 万条补追光线约 4 ms，加阴影光线约 1.6 ms。

### 补追光线按粗糙度分布（`rMax` = 1，占整幅画面的比例）

| 场景 | < 0.1 | 0.1–0.25 | 0.25–0.5 | 0.5–0.75 | ≥ 0.75 |
|---|---|---|---|---|---|
| `mirror-board` | 33.0% | 0 | 4.3% | 0.04% | 14.5% |
| `backlit-room` | 0 | 0 | 0 | 69.3% | 0 |
| `materials` | 0 | 0 | 6.1% | 13.2% | 70.8% |
| `cornell` | 1.4% | 0 | 2.8% | 48.1% | 0 |

- 粗糙度 ≥ 0.5 的补追份额很大：参考场景里大面积的墙面和地面粗糙度都在 0.5 以上（默认材质 0.92，`paint@1` 默认 0.6）。不加限制时，开销随粗糙表面的覆盖面积增长，`r_max` 取 0.5 就把这部分去掉了。
- 粗糙表面（≥ 0.5）的补追会改变画面：`cornell` 的平均差 2.0 级，限到 0.5 时剩 0.4 级。这是封闭空间里粗糙墙面本应得到的、来自屏幕外的高光；限到 0.5 后，这部分要等 S2 的探针来补。

### 存储缓冲上限

- **本机**：Chrome 145 在 core 下给每个阶段 10 个存储缓冲（适配器上限）。
- **`maxStorageBuffersInFragmentStage` 读不到**：Chrome 145 还没有暴露这个上限。
- **compatibility 在本机测不出来**：以 `featureLevel: 'compatibility'` 请求适配器，拿到的仍是 core 适配器（规范允许：实现无法执行 compatibility 的限制时，按 core 处理）；它的设备默认值就是 core 的默认值（每阶段 8 个存储缓冲，绑定上限 128 MiB）。
- **按 WebGPU 规范**（W3C WebGPU，limits 表）：
  - 片元阶段的存储缓冲默认上限，core 为 8，compatibility 为 4；
  - 顶点阶段为 0。
- **两种做法的需求**：
  - A 在片元阶段要绑 5 个存储缓冲：BVH 4 个，加材质表；
  - B 在 compute 阶段要绑同样的 5 个，外加 1 个存储纹理，片元阶段只多两个颜色目标。

  所以在 compatibility 设备上，A 要么请求超出默认值的上限，要么把材质表改成纹理（降到 4 个）；B 不受片元阶段上限的约束。

## 回答 U3

- **在哪里补追：推荐 A（SSR 的片元着色里）。**
  - 出图与 B 相同，每帧便宜 0.3–0.8 ms，不需要额外的 MRT 目标和 pass，改动集中在 fork 的 `SSRNode` 一个文件里。
  - 代价是需要片元阶段的存储缓冲：core 设备（包括本机）都满足；compatibility 设备按 U4 的「质量层」规则，能力不足时不构建这一层，不必为它走 B。
  - 如果以后要在 compatibility 设备上开启，或者要给补追光线做压缩排序，再改走 B。B 的原型已经验证过，接口不变，都是在重投影之前并入原始采样。
- **`r_max`：建议视口取 0.5，导出（最终质量）取 1.0。**
  - **视口**：0.5 时，参考场景每帧只多 0.1–0.9 ms；取 1.0 时，粗糙表面多的场景每帧多 4.5–6 ms。在压力场景的规模下，后者会超过每帧的预算。
  - **导出**：有收敛帧数和时限，取 1.0 能得到封闭空间里粗糙表面来自屏幕外的高光，`cornell` 上多出 1.5 级的平均差。
  - S2 的探针接入以后，粗糙反射在视口里由探针补；导出是否仍取 1.0，到时由 S2 对照决定。Epic 把「粗糙反射复用探针」列为后续增强。
- **补追的接口**：fork 在片元末尾加上「补追份额 × 着色 × GGX 权重」，没命中的像素取补追的距离（乘以镜面主导因子），下游的 `cover`、重投影和降噪都不变，与 Epic「屏幕外反射」的写回规则一致。

## 顺带发现（S1 需要处理）

1. **three 的 `ggxReflectionSample` 在正对摄像机的表面上返回 NaN**（`examples/jsm/tsl/utils/SpecularHelpers.js`）：
   - 它先 `normalize(cross(up, N))`，再检查长度是否小于 1e-3，顺序反了。视空间法线恰好是 `(0, 0, 1)` 时，归一化得到 NaN，NaN 的长度比较为假，备用的参考向量就始终不会启用。
   - 在 `cornell` 里，有 39 332 个待补追像素的方向是 NaN（画面的 2.5%），都在正对摄像机的后墙上。
   - 对补追的影响：NaN 方向的光线会遍历整棵树。修复前 `cornell` 的 A 一帧要 115 ms，修复后 9.6 ms。fork 现在只补追方向长度有限的光线。
   - 对产品现在的 SSR：这些像素的 SSR 也失败，回退到 `envSpec`。产品的预通道法线是 8 位，量化后恰好落在 `(0, 0, 1)` 的面积会更大。
   - S1 本来就要 fork `SSRNode`，可以一并带上修好的采样函数，同时向上游报告。
2. **TSL 在 `Switch` 的各分支间共享的表达式会读到未赋值的值**：
   - 被多处引用的表达式，TSL 会在它第一次被构建的地方存成变量。如果那个地方是第一个 `Case` 的分支，其他分支执行时，那个分支没有运行，读到的就是未赋值的变量。
   - 原型里 `materialAt` 的法线输入在 14 个分支间共享，结果 `materials` 里 `fabric@1` 的命中点算出 NaN：A 的 `output.max(0)` 把它压成了 0（黑），B 则一路传到合成。修法是在 `Switch` 之前把所有输入存成变量。S1 的命中点材质表要遵守这一点，最好加一个检查（例如对照组 3 的逐网格误差）。
3. **一个网格有多个 group 时，每个 group 是 BVH 的一个根，在顶层各占一项、各占一个变换槽**：
   - 参考场景的 `box@1` 每个面一个 group，`cornell` 的 9 个网格在顶层是 44 项。打包层预留空间时要按根数算（`TraceLayer.need` 已改）。
   - 这对 S1 反而是便利：多槽位模型的每个槽位天然有自己的变换槽，材质索引可以直接按「实例 + 槽位」写进去，正是 Epic「精度分档」要的查表方式。
4. **three 的时间戳在嵌套 pass 里归属不准**：在别的 pass 的 `updateBefore` 里渲染的 pass，时间戳会记到错误的类别里（只有 SSR 时，全部时间都记在 `compute` 名下）。S1 和 S2 的性能用例要用墙钟（等 GPU 完成），或者逐 pass 计时。
5. **three 的帧编号只在动画循环里前进**：`PassNode` 和 SSR 的噪声每帧只更新一次，而帧编号只随 `requestAnimationFrame` 前进。在一个循环里连续 render，后面的帧会复用前一帧的 pass 结果。原型每帧前显式推进 `nodeFrame.update()`。S1 的导出帧循环如果不经过动画循环，也要注意这一点。
6. **B 的两张额外目标在背景处保留清屏值**：背景像素被 SSR discard，`ray` 和 `weight` 目标就停在清屏值 `(0, 0, 0, 1)`，compute 必须按深度跳过背景，否则会对整片天空发零方向的光线（修复前 B 每帧多 20 ms）。
