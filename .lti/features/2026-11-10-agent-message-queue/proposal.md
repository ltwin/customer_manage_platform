## Why

助手运行时输入框是锁住的，想追加要求或纠偏只能先停止、再重发，已经做到一半的工作会被打断。Codex、Claude 等 Agent 产品的做法是：运行中写的消息默认排队，等这一轮结束再发；需要立刻纠偏时，可以把某条排队消息“插队”送进正在运行的这一轮。

## What Changes

- 运行中（`queued` / `running` / `waiting_client` / `reconciling`）输入框可以照常输入。输入框有内容时按钮是「发送」，点击或回车会把消息加入排队；输入框为空时按钮仍是停止（沿用「停止运行」）。
- 排队的消息显示在输入框上方，按加入顺序排列。每条有两个操作：「插队」和「删除」。消息原样保留发送时的内容：文字、@ 引用、附件、Skill、场景上下文。
- 排队只存在当前浏览器标签页（owner 2026-11-10 拍板：只存前端）。刷新页面后还在，换标签页或换设备看不到，服务端不知道它的存在。
- 运行正常结束（`succeeded`）后，队首消息自动作为下一轮发出，其余继续排队，一轮结束发一条。运行被停止（`cancelled`）、失败（`failed`）或中途出错（`partial`，已有部分回答）时，队列暂停，不自动发送，队列上方出现「继续发送」（owner 2026-11-10 拍板停止和失败暂停；`partial` 也是出错，按同一规则处理）。
- 「插队」：消息立刻离开队列，出现在对话里当前这一轮中，位置就是它插入的地方。服务端接收后把它记成这次运行的一条补充输入，在下一次调用模型前送达；当前工具调用不会被打断。「已接收」不等于「已送达」：如果运行在送达前被停止、出错或超时，这条消息留在对话里，并标明“助手没有读到这条”。
- 插队落空时，同一个运行再跑一轮来回应这条消息（owner 2026-11-10 拍板）。落空指插队在模型输出最终回答的过程中到达，模型没读到它。最终回答已经完整给出（已入账）之后，这一轮视为结束，插队被拒，消息回到队首，作为下一轮发出。
- 运行停下来等摄影师补充（`waiting_input`）时，队列不自动发送。对排队消息点「插队」，等同于把它作为补充发出。
- 补充输入扩展为可携带引用（owner 2026-11-10 拍板）：插队和等待补充都能带 @ 引用的素材与附件。摄影师在本轮亲手附带或引用的内容，由账号级的「发送前说明」同意覆盖（owner 2026-11-11 拍板），不要求出现在建运行时的授权清单里。服务端只核对四件事：素材属于本账号且可用、本轮授权没有撤销、授权包含预览图类别、模型支持图片输入。插队的消息沿用本轮的模型和场景上下文。
- 选了 Skill 的排队消息不能插队，只能排队等下一轮，因为一轮运行的 Skill 是固定的。本轮模型不支持图片时，带图片的消息也只能排队。这两种情况插队按钮置灰并说明原因。
- 插队与等待补充共用每轮 12 次的补充上限。超过上限时，插队被拒，消息回到队首，提示“这一轮不能再插入，会在本轮结束后发送”。运行处于 `waiting_input` 时被拒，运行仍在等待，队列不会自动发出，提示改为“这一轮不能再补充，停止本轮后点「继续发送」”。

## Acceptance Criteria

**排队**

- WHEN 运行处于 `running`，摄影师在输入框写下文字并按回车 THEN 同一帧里输入框被清空，消息出现在输入框上方的队列中，不发出任何请求，运行不受影响。
- WHEN 运行中输入框为空 THEN 按钮是「停止」；输入框有内容时按钮是「发送」，`aria-label` 为「加入排队」。
- WHEN 队列里有 3 条消息，运行以 `succeeded` 结束 THEN 只有第 1 条作为新一轮发出，其余 2 条仍在队列；这一轮也结束后，再发出第 2 条。
- WHEN 运行以 `cancelled`、`failed` 或 `partial` 结束，队列非空 THEN 不自动发出任何消息，队列显示「继续发送」；点击后发出队首一条。
- WHEN 队首正在自动发出时刷新页面 THEN 这条消息要么还在队列里，要么作为待确认的发送出现，不会两处都没有，也不会两处都有。
- WHEN 自动发出的队首被服务端明确拒绝 THEN 它回到队首，队列暂停并提示原因，输入框里正在写的内容不受影响。
- WHEN 对排队消息点「删除」 THEN 消息从队列移除，不发出请求。
- WHEN 队列非空时刷新页面 THEN 回到该对话后队列原样还在；在另一个标签页打开同一对话，看不到这个队列。
- WHEN 带附件和 @ 引用的消息排队后自动发出 THEN 发出的请求与当时直接发送这条消息的请求完全一致（相同的 segments、模型、Skill、场景上下文）。

**插队**

- WHEN 运行正在执行一个工具调用，摄影师对排队消息点「插队」 THEN 同一帧里消息离开队列，作为摄影师消息显示在这一轮中；工具调用不被打断，下一次调用模型时，模型输入里包含这条消息。
- WHEN 模型正在输出不含工具调用的最终回答，此时插队被接收 THEN 回答完成后运行不结束，同一个运行再调用一次模型来回应这条消息，之后才结束。
- WHEN 最终回答已经完整给出、运行还没关闭时点「插队」 THEN 插队被拒，消息回到队首；运行以 `succeeded` 结束后，它作为下一轮发出。
- WHEN 运行处于 `waiting_input` 时点「插队」 THEN 消息作为补充发出，运行继续，效果与在输入框里补充相同。
- WHEN 点「插队」后请求返回运行已结束 THEN 消息回到队首，按队列规则处理（运行正常结束时随即作为下一轮发出），不丢失、不重复发送。
- WHEN 这一轮的补充已达 12 次再点「插队」 THEN 消息回到队首，提示“这一轮不能再插入，会在本轮结束后发送”。
- WHEN 排队消息带 @ 引用的素材和上传的图片，本轮模型支持图片输入，点「插队」 THEN 下一次调用模型时，模型输入里包含这条文字和对应图片，效果与新消息里同样的引用一致。
- WHEN 插队引用本账号可用、但不在建运行时授权清单里的素材 THEN 插队被接收，模型能看到它。
- WHEN 插队引用其他账号的素材，或本轮授权已撤销 THEN 插队被拒，消息回到队首，什么都不会写入。
- WHEN 排队消息选了 Skill，或带图片而本轮模型不支持图片输入 THEN 「插队」置灰，悬停分别说明“选了 Skill 的消息只能排队”“当前模型不支持图片，只能排队”。
- WHEN 运行处于 `waiting_input`，摄影师在输入框附上图片并补充 THEN 补充带着图片发出，运行继续。
- WHEN 插队请求结果未知（网络断开、响应丢失） THEN 消息保持为待确认，界面提供「重新发送」；重新发送重放同一个请求，服务端只记录一次。只有服务端明确拒绝时，消息才回到队首。
- WHEN 运行处于 `waiting_input`，插队因达到上限被拒 THEN 消息回到队首，提示“这一轮不能再补充，停止本轮后点「继续发送」”。
- WHEN 插队后、模型读到之前摄影师点了停止，或运行出错 THEN 运行照常结束，这条消息留在对话里并标明“助手没有读到这条”，不再自动重发。
- WHEN 最终回答入账后、续跑开始前 worker 崩溃 THEN 恢复流程把运行结束为 `partial`，不会标成 `succeeded`；插队消息标明“助手没有读到这条”，队列暂停。

## Impact

- 代码：`frontend/src/creative-canvas/editor/`（AgentPanel 输入框、队列组件、agentState）、`backend/internal/creativeagent/`（运行中接收补充、落空时再跑一轮）、`api/openapi.yaml` 与两份生成物。
- 契约：扩展。新增插队接口；`supplements` 增加可选的引用片段；运行块新增 `input` 类型。已有请求和响应保持兼容。外发授权契约（`docs/product/creative-canvas-system/data-model.md`「外发同意的资源边界」）补一条：摄影师在本运行中亲手附带或引用的本账号内容，由账号级同意覆盖。
- 外部：无。

## Risk Notes

- concurrency：插队写入发生在 worker 正在执行这次运行时。补充输入要在模型调用的边界被读到，不能漏读也不能重复送达。落空判定（最终回答已出、插队刚写入）和结束运行之间存在竞态，需要在同一个锁或事务里确定“这条插队是否已被这一轮读到”。停止与插队同时发生时，以停止为准。
- trust-boundary：补充输入原来只有文字。带引用后，素材会发往模型供应商，而且本次放宽了逐修订清单的要求。仍然守住的边界是：只能是本账号且可用的素材（`RequireUsable`）；授权撤销后不能再发；派发前照常复核撤销与可用性（`admitDispatchInTx`）。逐资产授权整体收敛成账号级同意，另开 change 处理。
- 前端队列和运行状态都来自 SSE 快照，自动发送要避免同一条消息在多个结束事件、重连或多次渲染中被发出两次。
- 与进行中的 `agent-scene-mention`、`agent-run-context-limit-dead-end` 都改 `AgentPanel.tsx` / `agentState.ts`，合并时可能有文本冲突。
