# R1 性能（AC-R1-7）

e2e「AC-9」（`SCENE_E2E_PERF=1 SCENE_E2E_PERF_OUT=<本目录>/perf`；Apple M4 Pro，Chromium 145.0.7632.6，Metal，1600 × 1000、2× 像素，画布 2394 × 1692），约 200 个物件、8 种材质、太阳与 4 盏灯（2 盏聚光投影）。数据：`perf/perf.json`；R0 基线：`scene-webgpu-spike/discovery/research/baseline/perf.json`。

## 视口帧时间（毫秒，平均 / p95 / 最大）

| 模式 | R0 WebGL | R1 WebGPU | 结论 |
|---|---|---|---|
| 线框 | 8.3 / 9.2 / 9.4 | 8.3 / 9.1 / 9.4 | 不高于 |
| 白模 | 8.5 / 9.2 / 17.1 | 8.3 / 9.3 / 9.4 | p95 高 0.1 ms（刷新率上限处的噪声），平均与最大都更低 |
| 材质预览 | 15.2 / 17.4 / 17.7 | 8.3 / 9.2 / 9.3 | 不高于 |
| 最终渲染 | 19.8 / 25.8 / 30.9 | 8.3 / 9.2 / 10.9 | 不高于 |

四种模式都在 120 Hz 刷新率上限（8.3 ms），R0 的材质预览和最终渲染分别是 15.2、19.8 ms。

## 加灯、删灯时最长的一帧

| | R0 | R1 | 结论 |
|---|---|---|---|
| 加一盏点光 | 120 ms | 2808 ms | **高于基线，交 owner** |
| 撤销（删掉它） | 136 ms | 259 ms | **高于基线，交 owner** |

原因：WebGPU 的着色器把灯光写进代码，加一盏灯，每种受光材质都要重新编译渲染管线（本场景 9 条，每条片元着色器 55–65 KB）；Chrome 在 Metal 上编译管线时 GPU 进程不出新帧，异步编译也一样（实测管线全部经 `createRenderPipelineAsync` 后仍停约 2.5 s）。WebGL 时期的程序与渲染目标无关、可并行编译，所以 R0 只有约 0.12 s。

R1 已做的：

- 新灯按各 pass 的真实目标（MSAA、半浮点、法线 MRT）预编译。r186 的 `compileAsync` 稍后才逐个构建材质，届时灯光已被帧重置，所以改为编译一份独立的替身场景（每种网格一个、灯光拷贝）；之前编译的是画布格式，各 pass 首帧还要全部同步编译。
- AO 预通道改用覆盖材质画几何法线（与旧 GTAOPass 的 `MeshNormalMaterial` 相同），不再随灯光重编译。这两项把加灯从约 5.0 s 降到约 2.5 s，画面对照不变。

剩下的需要架构层面的选择（Epic 范围）：例如预留固定数量的灯光槽（多出的槽强度为 0），加灯在槽内时不重编译；或接受现状。

## 导出耗时

见 `parity.md`「导出耗时」：R1 WebGPU 在 noon、dof 上不高于基线，dusk、room、cornell 高 25–120 ms，materials（含玻璃）高约 300 ms（单次测量，含对话框流程）。每张图新建管线、首张图编译着色器是主要开销。逐项差距交 owner。

## 连续导出的纹理数

玻璃场景 16 台摄像机 × 3 种方式共 48 张：clay / line 恒为 5 张纹理、lit 恒为 10 张，不随张数增长（修正前 lit 每张多 1 张，见 tasks 6.1）。
