# Roadmap

## 子项

串行推进（policy: serial）：前一项归档并合回之后，下一项才进入实施；后面的子项可以提前准备设计。

排序原则：
- **P1 先做**：改动小、收益是数量级的，现有场景立刻受益，也给后面所有子项提供压力场景和每帧统计。
- **P2 在 P3 之前**：Skill 的自检流程要用负载摘要。
- **P3 在 P4 之前**：成本低，先改善助手搭场景的方式；P4 工作量最大，可以提前准备设计。
- **P5 独立**：可以排在 P4 前后任何位置，按当时的痛点决定。
- **P6 最后**：依赖世界空间 GI S1 的派生几何管线，穿刺先行。

### 验收责任

- 每个子项按自己的 proposal 验收，owner 接受后归档。
- 有几项**只能由 owner 判断**：
  - AC-2 每个子项的并排图，确认肉眼看不出差别；
  - AC-5 的场景观感 rubric；
  - P5 隔帧更新和 P6 LOD 的运动画面。

  技术检查通过不等于质量通过。
- 性能门禁按 `targeted-verification` 只在相关子项里定向运行，不进 `make check`（需要真实 GPU）。
- Epic 整体在 P6 归档后，按 proposal 的 AC-1 至 AC-8 验收。

## 后续项（不在本 Epic）

- **Alt+D 关联复制**（owner 2026-10-24）：模型实例的副本默认勾选「应用到全部」，与 Blender 的手感一致。需要在场景文档里记录关联组，属于数据契约改动，要先走 roadmap。
- **合并为模型**：把选中的一批基础体生成为一个代码模型，类似 Blender 的 Ctrl+J。等 P3 上线后，看实际是否需要。

## 与其他 Epic 的关系

- **`scene-world-space-gi`（active）**：
  - 它的光追底座按「实例 + 槽位」组织 BVH，多 group 的网格每个 group 一个根。P1 合并后每个 mesh 只有一个材质、没有 group，与这个组织方式一致；几何变少、变大，BVH 的数量也随之减少。
  - P4 实例化后，场景图里不再是一物件一 mesh。光追收集要通过批次层的逐物件清单读取（design「接口设计」），不能解析 `InstancedMesh` 内部。两边谁先合回，谁就按这个接口实现，另一方跟进（U2）。
  - P6 与它的 S1 共用派生几何管线（Worker、缓存、`meshoptimizer`）。
  - 它的 roadmap「建议另立：光栅的 LOD 和 cluster 剔除」由本 Epic 的 P6 承接。
- **`creative-mcp-server`（active）**：它的契约规定 MCP 的 `read_scene`、`edit_scene`、`write_model` 与内置工具结果相同，所以 `render_load` 会随之出现在 MCP 结果里，不需要它改契约。
- **`scene-editor-3d`（active）**：以后的外部 GLB 导入经 `partsOf` 加载，自动享受合并；按部件点选落地时，合并要记录每个部件的三角形范围（design「已知限制」）。
