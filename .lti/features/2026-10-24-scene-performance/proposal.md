# Epic: scene-performance — 场景性能与复杂场景承载

永久需求文档：本 Epic 的目标、边界和交付计划。整体方案见 design.md，目标契约见 contracts.md。项目 `.lti/contracts/` 记录当前已交付事实。排查过程与实测数据见 design「设计上下文」。

## 目标

场景稍一复杂，最终渲染的视口就会掉到个位数帧，白模也会掉帧，换 RTX 4090 的机器也一样（owner 2026-10-24 报告）。排查结论（design「设计上下文」）：

- 卡顿的原因是 **mesh 数量**，不是面数。three.js r186 的 `WebGPURenderer` 每次 draw 要花约 3 µs 的 CPU，每个 mesh 每帧要画好几次：白模约 2.2 次，最终渲染 5.5–6.5 次（4 级阴影级联占大头）。所以帧时和 draw 数成正比，与显卡无关。
- 代码模型的每个 `Mesh` 都原样成为一次 draw：`partsOf` 不合并，沙箱又禁止 `InstancedMesh`。用循环搭出来的模型，一个就有几百上千个 mesh。
- 到世界空间 GI Epic 定的规模（2000 万面、2000 个实例）时，第二个瓶颈出现：光栅本身每帧 68–78 ms（GPU，`scene-world-space-gi` S0），那时受限于三角形吞吐。

**画质优先**（owner 2026-10-24）：性能优化不以渲染效果为代价。优化前后画面要相同；确实有差异的，只允许肉眼难以分辨的程度。达不到时调低性能目标，不降画质。

本 Epic 完成后：

1. **系统层兜底**：不管内容从哪来（助手写的代码、创作者改的代码、资产库、以后的外部 GLB 导入），也不管怎么复制出来，渲染端都按内容合并、共享和实例化，帧时不再随物件结构线性恶化。到 2000 万面的规模时，由光栅 LOD 接手三角形吞吐。
2. **成本看得见**：助手读写场景时能看到渲染负载（档位和主要来源），创作者能在视口打开统计叠加层（物件、三角面、每帧绘制次数、帧时间），和 Blender 的 Statistics 一样。
3. **方法教得会**：新增内置建模 Skill，教助手做只有作者才能做的结构决策：成批小件写成一个代码模型、重复的东西放同一模型的多个实例、槽位怎么划分、投影灯的代价。也教它不该做的事：不要为了性能降低分段数。

## 范围与非目标

- **范围**：
  - **渲染批次**：模型 part 按材质合并、基础体几何按参数共享、相同物件自动实例化，以及每帧负载统计。
  - **阴影**：与相机无关的阴影（聚光、点光）只在投影物或灯光变化时重画，静止收敛帧不重画太阳级联；远处级联在运动时隔帧更新，由实测决定要不要做。
  - **渲染负载**：服务端为助手估算渲染负载，在 `read_scene`、`edit_scene`、`write_model` 的结果里返回；编辑器视口加统计叠加层；工具说明加一句成本模型。
  - **建模 Skill**：`deploy/creative-skills/` 新增内置包，附固定任务评测。
  - **光栅 LOD**：穿刺先行，与世界空间 GI 共用派生几何的生成管线（Worker、缓存、`meshoptimizer`）。这一项承接 `scene-world-space-gi` 修订 v3 建议另立、owner 同意提前排期的「光栅的 LOD 和 cluster 剔除」。
  - 可选开启的性能门禁：e2e 压力场景和帧时记录。
- **非目标**：
  - **Nanite 式的虚拟几何与 GPU 驱动渲染**：owner 2026-10-20 已决定不做（问题不匹配，WebGPU 也缺 64 位原子操作）；WebGPU 核心规范也没有 multi-draw-indirect。
  - **Alt+D 关联复制**：编辑语义，与性能无关，作为后续单独的小功能（owner 2026-10-24）。
  - **在模型代码里合并**：沙箱 `lib` 不加 `merge`，Skill 也不要求作者合并。合并只在渲染端做，GLB 和 manifest 保留部件结构。
  - **改模型内容或场景文档的数据契约**：本 Epic 不新增存储字段。渲染负载是读时派生，不存储，也不进渲染指纹。
  - **限制或拦截写入**：负载只提示，不拦截（「给能力不加闸门」）。
  - **任何肉眼可见的画质代价**（owner 2026-10-24）：例如运动中降低分辨率、关掉 AO、减少阴影级数、降低分段数。阴影隔帧更新和 LOD 只在肉眼难以分辨时才做，由 owner 看图决定。
  - **导出和 `render_view` 用简化几何**：LOD 只用于视口，出图一律用完整几何。

## 接口约定

目标契约在本 Epic 的 `contracts.md` 中定义：

- `patterns: ADD 场景渲染批次`：物件 group 是身份、变换和拾取的唯一来源；合并、共享与实例化都是渲染端的派生状态；合并只在加载后进行，模型代码不负责合并；性能按每帧 draw 数衡量。
- `architecture: ADD 场景渲染负载`：渲染端的批次层和负载统计、服务端的负载估算，以及它们的依赖方向。
- `api: ADD 场景渲染负载`：`render_load` 对象，由内置助手工具 `read_scene`、`edit_scene`、`write_model` 返回；MCP 暴露的同名工具结果相同。

场景命令、客户端任务、模型内容、GLB 子集和渲染指纹都不变。

## 验收标准

参考设备沿用 `scene-webgpu-renderer` 的规定（owner 的日常设备，现为 Apple M4 Pro），视口 1600 × 1000、2× 像素。压力场景由 P1 提交为 e2e 固定数据（design「验证与交付」）。

- **AC-1 多部件模型**：
  - **WHEN** 场景里有 4 个代码模型实例，每个 1000 个 part（2 个槽位），**THEN** 白模、材质预览、最终渲染（工作台和实时 GI）的视口帧时都不超过 16.7 ms。
  - 排查时的基线：白模 16 ms、工作台最终渲染 63 ms、实时 GI 84 ms；同一场景在 GLB 里预先合并后是 8.3–8.7 ms。
- **AC-2 画质不降**（每个子项都要满足）：
  - **WHEN** 同一场景在优化前后各导出一次 `clay`、`line`、`lit`（工作台和实时 GI），**THEN** 差异在迁移等价阈值内（`line` 平均差 ≤ 0.1、差 > 8 的像素 ≤ 0.05%；`clay`、`lit` 平均差 ≤ 1.5、差 > 8 的像素 ≤ 1%），并由 owner 看并排图确认肉眼看不出差别。
  - 合并 part（P1）、共享几何（P1）、实例化（P4）和阴影缓存（P5）都按「本应相同」验收，不留例外。场景里要包括同一槽位互相重叠的半透明面、幽灵模型、选中描边和线框模式。
  - 只有隔帧更新（P5，可选）和 LOD（P6）允许近似，它们另由 owner 在镜头运动中看图判断。
- **AC-3 规模场景**：
  - **WHEN** 场景有 2000 个模型实例（来自约 30 个代码模型，每个 20–300 个 part）、300 个基础体、总计不超过 500 万面、4 盏投影灯（太阳、2 盏聚光、1 盏点光），**THEN** 镜头运动时白模的视口帧时不超过 16.7 ms，最终渲染（工作台和实时 GI）不超过 33 ms。
  - 这组阈值是待验证假设：由 P1 测基线、P4 和 P5 实测后，经 Epic 修订确认或调整。
- **AC-4 负载可见**：
  - **WHEN** 助手调用 `read_scene`，**THEN** 结果带 `render_load`；在 P1 的压力场景上，估算的每帧绘制次数与实测相差不超过 ±25%。
  - **WHEN** 写入后负载达到「中」或「重」，**THEN** `edit_scene`、`write_model` 的结果带 `render_load`。
  - 编辑器可以打开统计叠加层，显示实测的物件数、三角面、每帧绘制次数和帧时间。
- **AC-5 Skill**：
  - 在固定任务集上，例如「一条 40 根柱子的哥特长廊」「一个摆满书的书架」，助手搭出的场景负载不是「重」，成批的小件用了阵列或实例，没有为性能降低分段数。
  - 场景观感由 owner 按 rubric 判断，评测通过不等于质量通过。
- **AC-6 阴影**：
  - **WHEN** 只有镜头在动，**THEN** 聚光和点光的阴影贴图不重画。
  - **WHEN** 视图静止、实时 GI 在收敛，**THEN** 太阳级联不重画。
  - 视口每一帧的阴影都与改前逐像素一致；导出总是重画。
  - 远处级联隔帧更新只有在 owner 看过运动中的画面、确认肉眼看不出拖影后才做。
- **AC-7 大规模**：
  - `scene-world-space-gi` 的压力场景（2011 万面、2000 个实例）的视口帧时目标由 P6 穿刺提出，owner 确认后经 Epic 修订回填。
  - LOD 只用于视口，误差和切换在静止和运动中都要肉眼看不出，由 owner 看并排图和运动录像确认。
  - 导出和 `render_view` 用完整几何。
- **AC-8 不回退**：参考场景集的导出对照不变；导出仍然确定，同一场景两次导出逐像素相同。

## 交付路线

见 roadmap.md。P1 先交付，现有场景立刻受益；光栅 LOD 穿刺先行，远期目标临近实施再细化。

## 决策记录

- **2026-10-24 owner**：
  - 采用「系统层 + 工具 + 建模 Skill」三层一起推进。
  - 合并在渲染端自动做，不做成助手的选项。
  - 规模目标对齐世界空间 GI Epic。
  - `read_scene` 的负载摘要是新增字段，不升工具版本。
  - 阴影先只做「不该重画时不重画」，远处级联隔帧更新等 P5 实测后再定。
  - Alt+D 关联复制作为后续单独的小功能。
- **2026-10-24 owner**：性能不能以渲染效果为代价，至少要做到肉眼难以看出区别。因此：
  - 合并改为严格等价：半透明槽位和幽灵模型按网格片绘制，描边和线框按网格片生成；
  - 画质成为每个子项的准入条件；
  - 出图不用 LOD；
  - 性能目标在画质约束下确定，达不到时调整目标。
- **2026-10-24 修正**：此前说过「不做 LOD」，只对当前的卡顿成立。在 2000 万面的规模下，光栅受三角形吞吐限制（GI S0 实测），所以把光栅 LOD 作为 P6 并入本 Epic，穿刺先行。Nanite 仍然不做。
