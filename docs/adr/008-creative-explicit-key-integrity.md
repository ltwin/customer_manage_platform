# 新创意空间采用显式 key 与领域事务维护引用完整性

## 背景

摄影师明确要求：新创意空间尽量不用数据库外键，采用显式 key 联表，以降低新对象类型、跨生命周期引用和删除编排演进时的结构耦合。2026-09-09 已据此修订设计；本记录使该决策与仓库早期选型依据的适用范围可追溯。

[ADR-002](002-postgresql-as-primary-store.md) 选择 PostgreSQL，并将库层外键作为当时 CRM 关系模型的收益。本 ADR 只替代该收益在**新创意空间业务表**上的默认适用，不否定 PostgreSQL 选型，也不要求删除现有 CRM/先导约束。无外键是明确承担维护成本的工程取舍，不意味着外键阻止 JOIN 或只有去掉外键才能扩展。

## 决策

- 新创意空间业务表不创建数据库外键，包括 account_id；仍保留账号作用域、主键、业务唯一约束、NOT NULL、单行 CHECK 与查询索引。
- 引用采用显式账号与对象 key；画布内关系同时验证 canvas_id。所有写入在领域事务内核对存在性、账号、类型、状态和归属，不接受客户端账号身份作为授权依据。
- 新增引用与删除使用同一根锁/目标锁；绑定内容只接受 ready 修订和 blob。删除、提升子组、解绑和保留释放由领域命令显式执行，不采用数据库自动级联或 ORM 隐式关联。
- 历史来源 key 与正常引用区分：历史来源允许按保留契约失效，正常引用缺失必须记录异常并停止相关破坏性清理。
- HTTP、Agent、worker、导入、迁移共用上述守卫。原始 SQL 写入不会得到外键保护，禁止把绕过守卫的脚本当普通业务入口。
- 现有 CRM/先导表、River 内部 schema 和旧迁移保持原样；全项目统一改造不在本次授权范围。

## 代价与交付约束

应用代码承担引用完整性；漏接 writer、遗漏清理顺序和并发预查都会产生悬空关联。数据库外键原本可提供的一部分防线需要集成测试及只读扫描覆盖；类型、用途、撤销、媒体保留等业务规则仍须由领域处理。

首个持久化开发切片同时交付该切片的关联归属清单、事务守卫、服务拒绝悬空/跨账号引用测试、删除并发测试与可运行的一致性扫描。新增关系扩展同一清单和扫描，未覆盖的关系不得进入破坏性 GC；扫描发现异常先隔离和核实，不自动删除疑似孤立媒体。

具体关系与统一锁序以[数据模型](../../../docs/product/creative-canvas-system/data-model.md)为权威，本 ADR 不重复维护 SQL 和状态机。

## 未采用的方案

- 混合外键：技术上可行，但不符合本轮已确认的新业务表方向；不能借 `NO ACTION` 或账号归属例外重新引入。
- 仅在事务外查询存在性：不能抵御并发删除。
- 泛化关系引擎：本期只维护所属模块的明确关系及检查，不构建任意关系运行时。

该决策已获得摄影师授权；不代表 DDL、扫描器或生产验证已经完成，也不代表整个 Epic 已进入开发。
