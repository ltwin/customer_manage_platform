# 创意空间计费与预算系统需在独立分支整改

## 1. 决策与范围

Owner 于 2026-10-10 明确要求：计费系统后续单独开分支重点处理；当前先记录 issue，并暂时放宽额度以支持功能测试。本次不实现正式计费整改、不创建后续分支、不清除历史费用或未结算证据。

## 2. 复现与证据

当前生图每次按最大文字输入、9 张参考图、4 张输出的统一上界预留 2.112200 USD，不随本次实际数量、参考图数量、分辨率等收紧。因此当前剩余额度不足，且“调整参数”并不能降低这笔固定预留。

Krill 本次只接入 GPT 对话；生图仍使用 AiCodeWith。不同供应商与对话/生图共用账号月度预算，Krill 钱包余额不会自动改变平台预算。

## 3. 后续独立分支需处理

1. 明确平台预算、供应商钱包、预估、预留、实际费用与未知结算的语义，界面分别呈现。
2. 为超时、取消及进程中断后的未知请求提供可审计的核实与人工处理入口；明确供应商无法查询时的处理政策，不能把未知费用当作零。
3. 审视 Agent 单次预留和生图固定最坏上界，按可证明的本次请求边界收紧预留；保留防止重复计费、超额及并发竞争的约束。
4. 明确模型价格、长上下文、缓存读写、渠道折扣、钱包单位和币种换算；区分保守预算账与真实账单。
5. 额度不足返回明确原因、当前上限、已用/占用/可用、所需预留及可行操作；仅在确实可恢复时提示稍后重试。
6. 解决配置与持久化预算不同步：目前 `.env` 影响新预算/调用组，已存在的 `llm_budgets` 与调用组仍读取落库上限；设计正式额度变更、审计和生效机制。
7. 明确跨供应商及对话/生图共享额度是否符合产品预期，提供可观测性。

相关实现：`backend/internal/platform/llmgateway/admission.go`、`generation_admission.go`、`generation_policy_price.go`、`generation_aicodewith_policy.go`、`backend/internal/platform/httpapi/creative_canvas.go`。

## 4. 本次临时测试措施

- 仅在 `feat/creative-workspace-redesign` 工作区本地 `.env` 设置 `CREATIVE_LLM_MONTHLY_LIMIT_MICROS=10000000000`（10,000 USD）、`CREATIVE_LLM_MONTHLY_TOKEN_LIMIT=1000000000`（10 亿 token）。生产默认值及 `.env.example` 默认说明不变。
- 将当前测试账号 2026-10 的 `llm_budgets` 对应行上限同步提高到上述值；保留预留、已记账、token 用量、请求状态及全部结算证据。
- 额度放宽不代表供应商充值或免费调用，账本仍正常记账。
- API 和 creative-worker 重启后读取新配置，新调用组及后续月份采用新的上限。历史调用组保持冻结值，恢复测试应发起新的运行。
- 正式计费分支交付前复核并撤销或替换该临时配置；降低额度时保留实际支出和在途预留，不倒改历史证据。

执行结果：已更新本地两项配置，数据库事务成功提交且仅更新一行。本月可用额度变为 9,980.971649 USD；预留 18.042880 USD、已记账 0.985471 USD，以及 token 预留/已用均保持原值。`.env` 已确认由 Git 忽略。本次只改文档、环境配置及明确授权的测试额度，未发起付费生成，未创建提交。

## 5. 验收方向

- 未知结算、核实释放与实际结算具备幂等证据；取消和重启不泄漏并发许可、不重复扣费。
- 并发准入遵守额度，费用与 token 的预留/结算一致。
- 已存在的月度额度能按明确政策调整，配置变更不再静默失效。
- 提示准确区分平台预算不足与供应商余额不足，展示可行动的解决方法。
- 供应商切换不抹掉旧费用，测试环境临时放宽不会无意带入生产。

## 7. 同日后续决定：先落地对话容灾

Owner 后续明确授权对话失败重试与跨供应商切换，并要求暂不实现熔断。该工作在当前分支独立落地：每家首次调用后额外重试最多 5 次、间隔 5 秒，随后换下一家；耗尽后前台结束运行，费用仍单独待核实。旧 unknown 请求不自动重发。本 issue 的计费核实、上界收紧、精确结算和临时额度回收继续保留待办，不因容灾实现而关闭。

## 8. 容灾与预留的叠加限制（2026-10-10 评审）

对话容灾的每次尝试独立按上界预留，未知结果不释放。默认 20 USD / 500 万 token 月度上限下，连续 5xx 时 GPT-6 Astra 约第 3 次、Sol 约第 6 次即无法再准入，单轮最多可占用接近整月额度。当前实现在重试中途额度不足时先试下一家，仍不足则结束路线并返回额度不足（`creative_llm_budget_exceeded`），不再停留在进行中。根治依赖本 issue §3 的核实释放与预留收紧；被重试取代的 failed 请求已可通过 `VerifyUnacceptedInTx` 核实释放。

## 7. 供应商无法查询时的处理政策（owner 2026-10-14）

复现：本地服务运行中笔记本睡眠，醒来后 Agent 运行因超过期限结束，前台持续显示「已发生的费用仍在核实」。查库：同一运行里一次网络中断后被重试替代的调用、一次睡眠期间被巡检判为 `orphaned_dispatch` 的调用，都停在 `unknown`，各占约 $7.2 hold（按最大输出预留）；库里另有 4 笔同类。原因是 `VerifyUnacceptedInTx` 没有任何生产调用方，`unknown` 没有出口，Agent 巡检也随之每轮空转。

政策：派发满 10 分钟仍无结论的 Chat attempt，由 creative-worker 巡检 `SettleUnverifiable` 按估算结清——输入按预留时的输入上界计（1 字节 1 token、未命中缓存的上界单价，实测约为真实输入的 3–4 倍），输出记 0；hold 全部释放，请求置 `failed`，运行结算随之变为已结清。估算证据等级低于账单、用量推导和核实未受理，之后到达的真实证据会替换它。上文整改项第 2 条中「供应商无法查询时的处理政策」据此落定；核实/人工入口、上界收紧与精确结算仍按原待办保留。
