# 助手上下文压缩

## 0. 结论

| 决定 | 内容 | 来源 |
|---|---|---|
| 目标 | 长会话里，较早的对话不再被整段丢弃，而是整理成一份交接摘要继续带给模型；创作者看到的对话记录一条不少 | owner 2026-10-14 |
| 窗口配置 | 每个模型在目录里新增 `context_window_tokens`（运营使用的有效窗口），不超过模型能力上限 `capability.context_tokens`；没配时等于能力上限 | owner 2026-10-14；本设计 §2 |
| 触发阈值 | 有效窗口的 80%，平台统一配置，账号不可调 | owner 2026-10-14 |
| 计量单位 | 全部按 token 判断，不再把字节和 token 混在一起取最小值；以上一次模型请求的真实 token 用量为基线，新增部分按会话自动校准的比例估算；本期不接分词器 | owner 2026-10-14；本设计 §3 |
| 机制 | 参考 Codex：用会话当前的模型写一份结构化交接摘要，保存为**压缩检查点**；之后的运行按「检查点摘要 + 检查点之后的完整轮次」组装历史 | Codex `compact.rs`；本设计 §4、§5 |
| 原始消息 | 不改、不删；`read_history` 仍能读到压缩前的原文 | 本设计 §4 |
| 压缩后的上下文 | 系统指令 + 本轮 Skill + Skill 索引 + 摘要 + 压缩前的创作者原话（20k token 以内）+ 最近 2 轮完整对话 | owner 2026-10-14；本设计 §5 |
| 摘要写法 | 按固定小节滚动更新，每次在上一份摘要的基础上增补和修改；引用只留 `<<<内容修订 ID>>>`；不转述 Skill 正文 | owner 2026-10-14；本设计 §6 |
| 多个 Skill | 本轮选定的 Skill 加载正文；会话里用过的其他 Skill 只放索引；模型可以用 `load_skill` 按需加载本会话用过的固定版本 | owner 2026-10-14；本设计 §7 |
| 一期触发 | ① 提交新一轮时预计超过阈值，运行开始前先自动压缩；② 创作者输入 `/compact [关注点]` 手动压缩 | owner 2026-10-14；本设计 §8 |
| 兜底 | 压缩失败时，退回现有的「丢弃最早整轮」截断，不能挡住这一轮 | 本设计 §8.4 |
| 授权撤销 | 会话的外发授权被撤销时，这个会话的全部检查点失效 | 本设计 §9 |
| 计费 | 压缩消耗的 token 记入所在运行的用量，和普通对话一样按用量扣 | 积分计费方向（2026-10-14 拍板）；本设计 §10 |
| 称谓 | 模型能看到的文字一律用「创作者」，不再写死「摄影师」；本期同时修改基础指令与工具描述 | owner 2026-10-14；本设计 §12 |
| 用量指示 | 输入框旁放一个百分比小环，展开后显示各部分占比、已用、剩余，以及距自动压缩还有多少；总数用真实用量，分项为估算；没发过请求的新会话显示空环，不给预估值 | owner 2026-10-14；本设计 §11.1 |

本期不做（见 §14）：

- 运行内中途压缩（一次运行里工具调用很多时）
- 按创作类型定制摘要格式

## 2. 窗口配置

两层配置，含义不同：

| 字段 | 位置 | 含义 | 校验 |
|---|---|---|---|
| `capability.context_tokens` | 模型与部署（已有） | 供应商的硬上限，是能力事实 | 已有：部署能力必须覆盖模型 |
| `context_window_tokens` | 模型（新增，可选） | 平台愿意每轮发送的有效窗口，是运营策略 | `0 < 值 ≤ context_tokens`；缺省等于 `context_tokens` |
| `AutoCompactRatio` | `Limits`（新增，平台级） | 触发比例，默认 0.8 | `0.5 ≤ 值 < 1` |

- **`context_window_tokens` 指单次请求的输入窗口**，不含输出。
  - 校验：`MaxOutputTokens + context_window_tokens ≤ capability.context_tokens`。
  - 内置模型默认 128k（owner 2026-10-14 同意按窗口推导）；2026-10-15 owner 调为 256k，此时字节上限为 1,024,000 字节，仍低于 `InputTextBytes` 的 1 MiB。
- 触发线 `compactAt = floor(context_window_tokens × AutoCompactRatio)`，比较对象是真实（或估算）的输入 token 数。
- 单轮可发送的历史预算 = `context_window_tokens − 指令、工具定义与本次提交的估算`，替代现在的 `contextBudget`。
- 要分两层，是因为所有模型的硬上限都是 1M，按 80% 算就是每轮重发 80 万 token，成本扛不住。
- `ModelSnapshot` 增加 `context_window_tokens`，运行按创建时的快照判断。目录修改不影响进行中的运行，与现有快照规则一致。
- 删除 `HistoryMessages = 20` 行数上限，改为扫描到最新检查点为止，另加一个防失控的扫描上限（默认 500 行）。

**单次请求的字节上限由窗口推导**（修订：原稿「`InputTextBytes` 调到 4 MiB」作废，owner 2026-10-14 确认）：

- **字节上限是花费上限，不是上下文上限。** 网关发送前不知道会算成多少 token，于是用「1 字节最多 1 token」作为保证不被突破的上界，按字节数预留额度，并拒绝超出预留的请求。首轮预留在运行创建时按字节上限计算。
- **为什么不能调到 4 MiB。** 那样以 Krill 的 GPT-6 Astra 为例，单次预留约 58 美元，超过账号默认的每月 20 美元，运行会全部被拒。
- **推导方式。** 字节上限 = `min(InputTextBytes, context_window_tokens × BytesPerWindowToken)`。
  - `BytesPerWindowToken` 是新增的 `Limits` 字段，默认 4。
  - `InputTextBytes` 保留（契约 `CreativeAgentLimits.input_text_bytes` 已对外暴露），含义改为全局封顶，默认从 256 KiB 调为 1 MiB。窗口配到 256k 以上时，由它兜住预留金额。
- **为什么乘 4。** 1 token 通常对应 3 到 4 字节：英文约 4 字符 1 token，中文每字 3 字节、约 1 token。乘 4 让字节线在正常文字下不会比 token 线先到，压缩时机只由 token 决定。
- **首轮预留对比**（窗口 128k，字节上限 512 KiB）：

  | 模型 | 现在 | 改后 |
  |---|---|---|
  | DeepSeek V4 Pro（高峰） | $1.87 | $2.21 |
  | GPT-6 Sol | $1.80 | $2.33 |
  | GPT-6 Astra（Krill） | $9.68 | $12.95 |

- **组装时两条线都守。** 历史按 token 预算组装，同时保证整次请求的字节数不超过字节上限，避免组装出在网关被拒的请求。

| | 单位 | 性质 | 管什么 |
|---|---|---|---|
| `context_window_tokens` | token | 软目标，到 80% 压缩 | 模型实际读多少（上下文管理） |
| 字节上限（窗口 × 4） | 字节 | 硬上限，超出拒绝 | 预留与花费的保证 |

`Limits.Version` 需要升级。

## 3. token 计量

按「真实用量做基线，校准估算补差」（owner 2026-10-14 确认，本期不接分词器）：

1. **基线**：本会话上一次成功的模型请求的 `InputTotalTokens + OutputTokens`。它就是上一轮结束时上下文的真实大小。
2. **增量**：基线之后新增的内容（上一轮最后的回复、本次提交的文字和引用、Skill 正文）按估算计入。
3. **校准比例**：每次模型请求发出前，记下这次请求文字部分的 UTF-8 字节数；拿到用量后算出
   `r = InputTotalTokens ÷ 字节数`，保存在该模型步骤上。估算新增部分时，用「新增字节数 × 本会话最近一次有效的 r」。
   - 没有可用的 r 时，用默认值 1/3（中文约等于字符数，英文偏高，整体偏保守）。
   - r 超出 [1/8, 1] 时视为异常（例如本次请求以图片为主），不采用，继续用上一个有效值。
4. **图片**：每张附加图片按 1,600 token 计，不参与校准。
5. **没有基线时**（新会话、或检查点之后还没成功请求过）：全部按校准比例估算。

**精度说明**：估算误差只作用在新增部分。例如有效窗口 200k、阈值 160k、基线 150k、新增约 5k，即使误差 ±30%，也只差 ±1.5k，不到窗口的 1%。防止溢出靠的是阈值之上 20% 的余量，比估算误差大一个数量级以上。

估算只用来判断要不要压缩、以及分配 §5 各部分的预算，不参与计费；计费仍以供应商返回的用量为准。

## 4. 压缩检查点

新表 `creative_agent_compactions`，追加写入，不就地修改：

| 列 | 说明 |
|---|---|
| `id`、`account_id`、`conversation_id` | 按账号隔离（ADR-001） |
| `run_id` | 产生这个检查点的运行 |
| `covers_through_ordinal` | 摘要覆盖到哪条消息（含），总是落在一轮结束处 |
| `previous_compaction_id` | 上一份检查点；滚动摘要的来源 |
| `summary` | 摘要正文，上限 32 KiB |
| `trigger` | `auto` / `manual` |
| `focus` | `/compact` 带的关注点，可空 |
| `model_key` | 写摘要用的模型 |
| `tokens_before` / `tokens_after` | 压缩前的真实或估算 token 数、压缩后的估算 token 数，用于对话里的分隔条 |
| `created_at` | |
| `invalidated_at` / `invalidated_reason` | 失效时间与原因（见 §9） |

- **生效的检查点** = 本会话 `invalidated_at IS NULL` 且 `covers_through_ordinal` 最大的那一份。
- 原始消息不做任何修改。界面照常显示完整记录；`read_history` 照常能回溯到检查点之前。

## 5. 压缩后的上下文组成

`freezeHistoryInTx` 改为按下面的顺序组装。`creative_run_inputs.input_role` 新增 `compaction_summary` 与 `skill_index`。

| 顺序 | 部分 | 来源 | 预算 |
|---|---|---|---|
| 1 | 系统指令 + 本轮 Skill 正文 | 每轮重新注入，不参与压缩 | 现有 |
| 2 | Skill 索引 | 由数据库确定性生成（§7），不经过模型 | 最多 20 条 |
| 3 | 交接摘要 | 生效检查点的 `summary`，带固定前缀（§6.3） | 上限 32 KiB |
| 4 | 压缩前的创作者原话 | 检查点覆盖范围内的 user 消息，从新到旧原样取用；超出预算时截断最后一条并标注「已截断」 | 20,000 token |
| 5 | 检查点之后的完整轮次 | 沿用现有整轮保留逻辑（成对保留工具调用与结果） | 剩余预算 |
| 6 | 本次提交 | 现有 | 现有 |

**最近 2 轮完整对话**：写检查点时，`covers_through_ordinal` 停在倒数第 3 轮结束处，最近 2 轮不进摘要，原样留在第 5 部分。

- 这样「刚才那个方案」总有对象可指，不需要另写特殊逻辑。
- 这是对 Codex 的有意偏离：Codex 压缩后只保留用户原话，会丢掉助手刚给出的方案。
- 最近 2 轮本身太大时，先按现有 `compactMessages` 截短其中的工具结果；仍超出则只保留最近 1 轮。

**运行内裁剪不变**：`BeforeModelRewriteState` 里的 `compactMessages` 仍是最后一道保护。它只处理带 `creative_history_group` 标记的历史，摘要和 Skill 索引不带这个标记，不会被删。

## 6. 摘要请求

### 6.1 输入

- **系统指令**：压缩专用指令，不带助手基础指令和工具定义。
- **上一份摘要**：如果有的话。
- **要压缩的消息**：从上一份检查点之后到新的 `covers_through_ordinal`，渲染成纯文本记录：
  - 创作者和助手的文字原样保留。
  - 工具调用写成「调用 名称（参数前 512 字节）」。
  - 工具结果保留前 1 KiB。
  - 读取内容类工具（`read_asset` 等）的结果，沿用 `read_history` 的处理：替换为「曾读取内容；正文请用 read_asset 重新读取」，不把正文写进摘要。
  - 引用一律写成 `<<<内容修订 ID>>>`。
  - 用过 Skill 的轮次前标注「[本轮使用 Skill：名称@版本 ID]」。
- **不发送**：任何图片、Skill 正文、推理内容。
- **超出窗口时**：从最早的消息开始删，再重试（Codex 的做法）；上一份摘要始终保留。

### 6.2 摘要结构

压缩指令要求严格按以下小节输出，没有内容的小节写「无」：

1. 创作目标与当前方向
2. 已定结论
3. 明确否决的方向（附否决理由）
4. 创作者的偏好与要求（尽量保留原话）
5. 关键引用：`<<<内容修订 ID>>>` 或节点 ID，每条一句说明它是什么
6. Skill 使用记录：用哪个 Skill 做了什么、产出了什么；**不转述 Skill 的指令内容**
7. 进行中与未完成：在跑的生成、等待确认的事项
8. 下一步

滚动规则：上一份摘要里的条目默认全部保留，只有被后来的对话明确推翻时才修改，并在条目里注明「已改为……」。`/compact` 带的关注点作为附加要求放进指令，不能改变小节结构。

压缩指令只用中性称谓「创作者」，不出现任何领域词，换成其他创作类型也能直接用。

### 6.3 摘要前缀

摘要放进上下文时，固定加上以下前缀：

> 以下是本会话较早部分的交接摘要，由之前的对话整理而成。原始消息仍保存在会话里：细节不确定时，用 read_history 查原文，用 read_asset 读取引用的内容；不要凭摘要猜测。

### 6.4 模型与参数

- 用会话当前模型。摘要质量与对话一致，也不用另配模型。
- 输出上限 `min(8192, MaxOutputTokens)`。
- 不调用工具，不开推理回传。

## 7. 多个 Skill

| 层 | 内容 | 是否带正文 |
|---|---|---|
| 本轮 | 本次提交选定的 Skill，与现在一样进入系统指令 | 带 |
| 索引 | 本会话用过的其他 Skill：名称、`skill_version_id`、一句话描述、用在哪几轮、当前是否可用 | 不带 |
| 按需加载 | 模型调用 `load_skill` 加载索引里的某个版本 | 调用后才带 |

- **索引的来源**：由 `creative_message_skill_refs` 确定性生成，不经过模型。只要会话用过当前轮以外的 Skill 就注入，与是否压缩过无关。这也顺带解决了「上一轮用了 Skill A，这一轮没再选，模型就拿不到 A」的问题。
- **`load_skill` 的扩展**：
  - **注册条件**：本轮 Skill 的 manifest 允许，或者索引不为空（满足其一即注册）。
  - **后端 `List`**：本轮固定的 Skill 加上索引里的版本。
  - **后端 `Get`**：只按版本 ID 读取冻结正文，每次重新检查停用状态、digest 和账号可读性；不解析成最新版。
- **权限边界**：按需加载的 Skill **只提供方法（正文和资源读取），不扩大工具范围**。运行可用的工具仍由创建时固定的 Skill（或无 Skill）决定。加载的 Skill 提到本轮没有的工具时，模型照常看不到那个工具。
- **摘要不转述 Skill 正文**：作者写的、有版本的指令，被模型改写后就成了没人写过、没人审过的第三份指令。这和拒绝同时引用两个 Skill 是同一条理由。

## 8. 触发与流程

### 8.1 提交时判断（自动）

在创建运行的事务里，按 §3 估算「当前投影 + 本次提交」的 token 数：

- **不到 `compactAt`**：和现在一样冻结历史，运行照常开始。
- **到了 `compactAt`**：运行标记 `compaction_pending`，**历史推迟到 worker 冻结**，其余输入照常冻结。

worker 接管后，第一步先执行压缩步骤（§8.3），成功后在同一事务里写入检查点并按 §5 冻结历史，然后进入正常的模型循环。

- 一次运行最多自动压缩一次。压缩后的投影仍然超过 `compactAt` 时，不再压缩，交给现有截断。
- 可压缩的内容不足（检查点之后不到 3 轮）时，跳过压缩。

### 8.2 `/compact [关注点]`（手动）

- **提交协议**：`CreativeAgentInstructionSegment` 新增 `type: command`，字段 `command: compact`、可选 `args`（关注点，上限 500 字符）。
  - 带 command 段的提交只能有这一段，不能同时带 Skill、文字或引用。
- **运行**：`creative_agent_runs` 新增 `kind`（`chat` / `compact`，默认 `chat`）。
  - compact 运行复用现有的准入、会话占用（同一会话同时只有一个运行）、租约、取消、事件流和计费预留。
  - 只执行压缩步骤，不进入模型循环。
- **触发消息**：照常写入会话，正文是 command 块。界面显示为一条命令记录，组装历史时跳过。
- **可压缩的内容不足时**：运行成功结束，结果说明「暂无可压缩的内容」，不调用模型。
- **手动压缩的范围**：与自动压缩相同，同样保留最近 2 轮。

### 8.3 压缩步骤

- 作为运行的一个步骤写入步骤日志，类型为 `compaction`。
- 模型请求走运行的调用组，受取消和租约约束。
- 接管恢复时，若步骤已有完整结果就直接采用，否则重新执行。

### 8.4 失败兜底

压缩请求失败（供应商错误、输出为空、结构校验不通过、超时）时：

- **自动压缩**：按现有逻辑冻结历史（截断），运行继续；事件流发出「上下文整理未完成，本轮使用较短的历史」。
- **手动压缩**：运行失败，如实报告原因；会话不变。

## 9. 授权撤销

- 会话的外发授权被撤销时（`consents.go:200` 写 `revoked_at` 的同一事务），把该会话所有未失效的检查点标为失效，原因是 `consent_revoked`。
- 下一轮没有生效的检查点，退回截断组装；超过阈值时重新压缩。
- 重新压缩的输入按 §6.1 渲染，不含任何读取内容的正文。所以新摘要带出的信息不会多于原始历史本身。
- 按会话整体失效，而不是精确到某个内容修订：实现最简单，代价只是多压缩一次。

## 10. 计费与用量

- 压缩请求是所在运行的一次普通模型请求，用量记入该运行，按「对话按用量扣」结算。
- 自动压缩发生在用户的这一轮里，费用合并在这一轮。
- `/compact` 是独立运行，单独显示用量。
- 运行的计费预留需要容纳压缩请求：输入上界按 `compactAt` 计，输出上界按 §6.4 计。

### 11.1 上下文用量指示

**数据从哪来**

- **总数**：最近一次模型请求的真实 `InputTotalTokens`，准确值，不标「约」。
- **分项**：供应商只返回总数。组装请求时按类统计各部分的字节数，再按比例分摊到真实总数上，保证分项之和等于总数。分项一律标「约」。
- **分类**：与 §5 的上下文组成一一对应。
  - **系统指令**：基础指令。
  - **工具定义**：按序列化后的大小计。
  - **Skill**：本轮正文、Skill 索引、按需加载的正文。
  - **交接摘要**。
  - **对话消息**：创作者原话与助手文字。
  - **工具结果**。
  - **图片**：按 §3 的每张固定值计。
- **记录位置**：每个模型步骤保存分项字节数、真实用量和校准比例 r（与 §3 共用同一份记录）。

**什么时候更新**

| 情形 | 小环显示 |
|---|---|
| 新会话，还没发过请求 | **空环**，不显示百分比，也不给预估值；展开后只显示「发送第一条消息后显示上下文用量」和当前模型的有效窗口 |
| 运行过程中 | 每次模型请求完成后，事件流推送一次 `context_usage`；工具调用多时可以看到占用实时上涨 |
| 打开已有会话 | 从会话详情读取最近一次记录 |
| 刚压缩完 | 按压缩后的组成估算，标「约」；下一次请求完成后换成真实数 |
| 输入框选的模型和上次请求不同 | 窗口按当前选中模型的有效窗口计算；分词方式不同，总数也改为估算，标「约」 |

**交互**

- **位置**：输入框右下角，模型选择旁边。
- **展开方式**：桌面端悬停展开，触屏点击展开。
- **展开内容**：
  - 标题：「上下文 已用 / 有效窗口 · 百分比」。
  - 一条进度条，标出自动压缩线。
  - 分项列表：类别、约多少 token、占比。
  - 底部：「剩余 X · 再用约 Y 后自动压缩」，以及「立即压缩」按钮（等同于 `/compact`）。
- **颜色**：中性色加一个强调色，不用渐变。
  - 60% 以下：中性灰。
  - 60% 到 80%：强调色。
  - 80% 以上：提示色，展开后说明「下一轮会先自动压缩」。
- **不计入**：输入框里还没发送的草稿。

## 15. 验收

1. **配置**：模型目录可以配置 `context_window_tokens`；超过 `context_tokens` 时目录加载失败；未配置时等于 `context_tokens`。
2. **自动触发**：会话上下文估算达到有效窗口 80% 后的下一次提交，先压缩再回答；对话流出现分隔条，运行用量里有压缩请求。
3. **手动触发**：输入 `/compact` 或 `/compact 保留配色讨论` 会产生一次 compact 运行和一个检查点；可压缩的内容不足时提示「暂无可压缩的内容」，不调用模型。
4. **原始记录不变**：压缩后界面显示的消息与压缩前完全一致；`read_history` 能读到检查点之前的原文。
5. **最近 2 轮**：压缩后，最近 2 轮的助手文字原样出现在下一轮的模型输入里。
6. **兜底**：模拟压缩请求失败，自动压缩的这一轮仍正常回答，并显示退回提示。
7. **授权撤销**：撤销后检查点失效，下一轮不再带该摘要。
8. **Skill 索引**：会话依次用过 Skill A、B，第三轮不选 Skill，模型输入里有 A、B 的索引但没有正文；模型调用 `load_skill` 能加载 A 的固定版本；停用 A 后加载被拒绝，索引里显示不可用。
9. **工具范围**：按需加载的 Skill 不让本轮多出任何工具。
10. **称谓**：称谓测试通过；基础指令与工具描述里不再出现「摄影师」。
11. **用量指示**：
    - 新会话显示空环，没有百分比和预估值。
    - 发送后，总数与该次请求供应商返回的 `InputTotalTokens` 一致，分项之和等于总数。
    - 运行中每次模型请求后都会更新。
    - 压缩后和切换模型后显示「约」。
    - 跨过 60% 和 80% 时颜色变化。
    - 「立即压缩」与 `/compact` 效果相同。
12. **连续性评测**：准备 5 段长对话样本，至少 1 段切换过 2 到 3 个 Skill，至少 1 段不是摄影创作（文案或视频脚本）。压缩后追问早期细节：否决过的方向、具体参数、某个引用的 ID、「按刚才用 X 做的思路再来一次」。答对率由 owner 评定是否达标；非摄影样本的摘要不得出现摄影领域词。

| 风险 | 说明 | 应对 |
|---|---|---|
| 摘要漏掉细节 | 压缩本质上有损 | 固定小节、滚动更新、创作者原话原样保留、`read_history` 可回溯、验收 11 评测 |

## 18. 实现记录（2026-10-14）

**§13「仍待调查」的结论**

- **步骤日志**：压缩记为 `creative_agent_steps.kind='compaction'`，由 `gateway.Call` 直接调用，不经过 Eino。
  `runExecution.run` 判断「有步骤却没有框架 checkpoint」时排除这类步骤；结算时按调用组归集请求，压缩请求自然计入。
- **计费预留**：运行创建时按首轮 binding（`#1`）预留。压缩步骤占用序号 1 接住这笔预留；第一次模型调用改为序号 2，
  由网关按实际字节另行预留。两次请求不需要预先合并成一笔。

**与设计稿不一致之处**

| 位置 | 设计稿 | 实现 | 原因 |
|---|---|---|---|
| §3 估算 | 基线 + 新增部分 | 用最近一次真实请求算出的比例估算整份投影 | 比例本身就由基线算出，未变化的部分估算值与实测一致；不用逐条追踪「基线之后新增了什么」，压缩后也无需特殊处理 |
| §5 顺序 | 摘要在前，创作者原话在后 | 同一条消息里原话在前、摘要在后，前缀紧贴摘要 | 与 Codex 一致；读到摘要时原话已在上文 |
| §5 条数 | 未规定 | 冻结历史最多 240 条消息，运行内兜底按 380 条裁剪 | 网关单请求最多 400 条消息 |
| §6.2 校验 | 未规定 | 只查实质：正常结束、至少 32 个字符、不超过字节上限；小节标题不作校验（2026-10-15 修订，原为「8 个小节至少出现 6 个」） | 真实模型（gpt-6-astra）改写了全部标题，按标题校验会丢掉可用摘要；与 Codex 一致，不校验结构 |
| §7 索引 | 含「当前是否可用」 | 不含；加载时重查可用性与 digest，停用时返回明确的拒绝说明 | 冻结时查可用性需要跨账号读取平台 Skill；加载时查更准确 |
| §7 资源 | 按需加载提供正文和资源读取 | 只提供正文；`read_skill_resource` 仍只读本轮固定的 Skill | 资源读取按运行固定的 digest 校验，扩展需要另行设计 |
| §11 契约 | 「会话详情」新增 `context_usage` | 消息分页的最新一页附带 `context_usage` | 现有接口没有单独的会话详情，打开会话读的就是消息分页 |
| §4 表结构 | — | 检查点表多一列 `composition` | 压缩后、下一次请求之前，小环按它显示估算的分项 |
| §2 推迟冻结 | 「历史推迟到 worker 冻结」 | 本次提交的输入从序号 `1<<20` 起写，worker 冻结的历史占用前面的序号 | 输入按序号读取，这样不用改读取逻辑 |
