# 策划文档与拍摄策划节点

## 0. 结论

| 决定 | 内容 | 来源 |
|---|---|---|
| 存储 | 策划是独立文档，存在 `creative_documents`，由 `internal.document` 骨架转正；不复用旧 `shootplanning` | owner 2026-10-15 |
| 内容形状 | 结构化骨架 + Markdown 正文：标题、基本信息、章节、图片引用、镜头是结构，文字是 Markdown | owner 2026-10-15 认可 |
| 图片位置 | 图片只在章节参考图组和镜头里，按内容修订引用；正文用稳定的引用标记指代图片 | 本设计 §2.3，评审 #3 |
| 模板 | 首版只有 cosplay SOP 模板 v1，固定、摄影师不可改；含准备清单章节；章节可标「本次不适用」 | owner 2026-10-15 |
| 版本 | 每次保存存一份全文快照，历史可看可恢复；标题也进快照 | 本设计 §4，评审 #4 |
| 并发令牌 | 每个冲突单元的 `rev` 取自文档修订号，单调递增、永不复用；恢复旧版本使所有旧令牌失效 | 本设计 §4.2，评审 #1 #2 |
| 确认 | 「已确认」绑定某个内容版本，只有摄影师能确认，之后任何修改都使确认失效 | 本设计 §4.4，评审 #7 |
| 审核 | 助手直接写入，不设待批准的建议层；「看改动」在原位显示自确认以来的差异；每轮结束给出改动清单，逐处对照「本轮之前 → 现在」，确认或恢复这一处 | 本设计 §7.7，交互走查 |
| 编辑器 | 所见即所得，存储仍是 Markdown 子集；不支持的内容明确提示，不静默丢弃 | owner 2026-10-15，评审 |
| 保存 | 按冲突单元串行提交的保存状态机，未保存内容本机留存；冲突时可择一，也可编辑出合并结果 | 本设计 §7.3，评审 #5，交互走查 |
| 放图 | 「添加参考图」选择器：当前画布 / 资产库 | 本设计 §7.2，评审 #6 |
| 视觉设定 | 分镜之前先定人设三视图与场景设定图；镜头记录用到的设定，分镜记录生成时的设定版本，设定更新后提示分镜过时 | owner 2026-10-15，本设计 §2.7 |
| 退出路径 | 文档回收站与彻底删除；彻底删除后图片才可被回收 | 本设计 §5.5，评审 #8 |
| 分层 | 通用层只管「节点 ↔ 文档」和存储；模板、校验、摘要、助手工具在新包 `creativeplan` | domain-design §2、§6 |
| 节点 | 新节点类型 `photo.shoot_plan`；卡片摘要由服务端从当前修订算出 | 本设计 §5 |
| 助手 | 新增 `read_plan@1`、`write_plan@1`；新建策划走 `edit_canvas` 的 `add_node`；按需读策划，不规定每轮先读 | 本设计 §6 |
| Skill 加载 | 不默认给消息挂 Skill；Skill 索引加入平台内置 Skill，助手第一次操作策划时自行加载模板配套的 Skill，加载过的留在上下文里；读到策划时服务端提示尚未加载 | owner 2026-10-15，本设计 §6.6 |
| 助手面板 | 编辑视图里嵌入画布的同一个助手面板，用同一个会话，不另做章节级 AI；章节、镜头、参考图和选中文字上的「请助手修改」只起草消息，带上这一处的标签；文档按画布记住工作会话 | owner 2026-10-15，本设计 §7.6 |
| 实时 | 不新增 SSE：`creative_documents` 已有账号级画布失效触发器 | 0042 迁移 |

本期不做：PDF 导出（结构为它保留，§8）、发布到订单、现场模式、分享给客户、复制为新方案、摄影师自定义模板、整轮一键撤销（随 V6-038；本期可按单元恢复，§7.7）、历史版本清理、从电脑直接上传图片进策划、文本级自动合并。

## 0.1 与通用文档底座对齐（2026-10-16）

通用部分抽成独立 change `creative-document-foundation`（`.lti/features/2026-10-16-creative-document-foundation/`，owner 2026-10-16 批准），策划和 3D 场景（epic `scene-editor-3d`）都复用。**本设计只实现 `photo.shoot_plan` 文档类型**；以下各节中与底座重复的部分改为引用底座，冲突时以底座的 design 和 contracts 为准。

| 方面 | 由底座提供 | 策划这边 |
|---|---|---|
| 存储 | `creative_documents` 补列、修订表（含 `unit_revs`、`annotated_units`）、引用表、工作会话指针表，迁移 0069 | 只加内容类型 `plan`（§3.1） |
| 单元版本 | 文档头和修订行的 `unit_revs`；标题单元固定为 `meta` | 载荷不再存 `title` 和各单元 `rev`；读取时把 `unit_revs` 合并进视图；`confirmed_rev` 仍在载荷里 |
| 命令外壳 | `POST /creative/documents/{id}/commands`：`expected`（值可为 null，表示预期不存在）、整批原子、409 `creative_document_conflict`（只列单元和修订号，客户端重读后进冲突界面）、有界回执（`reset_required`） | 策划的操作集合（§4.1） |
| 通用操作 | `rename`（单元 `meta`）、`restore`（带 `expected_revision`，按文档修订号检查）、`restore_units`（单独成批，可列多个单元；存在性变化时同时检查集合单元） | 「恢复后仍为已确认」用恢复钩子实现：读旧修订行的 `unit_revs` 判断 `confirmed_rev == rev`，是则把 `confirmed_rev` 设为新修订号 |
| 确认类操作 | 端口的 `Changes.Annotated`：载荷变化、修订号不推进 | `confirm_section` / `unconfirm_section` / `confirm_setting` / `unconfirm_setting` 都是标注操作 |
| 类型端口 | `creativedocument.Type`（含 `NodeTypeKey`、`Touched` / `Apply`、`RestoreTouched` / `RestoreUnits`、`Retain`、`View`、`Summary`） | `creativeplan` 实现，节点类型 `photo.shoot_plan` ↔ 文档类型 `photo.shoot_plan`（§5.4） |
| 画布接入 | `add_node` 建档与 `document_id` 放回、节点快照的 `document_summary` / `document_trashed` | 模板参数 `template_key` 经 `document_options` 传入 |
| 回收站与删除 | `trash` / `untrash` / `POST /purge`、文档列表、修订列表（`run_id`、`since_revision`）、读旧修订（可选 `units`） | 「引用已有策划」选择框、回收站入口等前端 |
| 权限 | 读 `creative_read`，摄影师写 `manual_write`；助手沿用运行授权检查 | 「仅摄影师」的操作由类型按写入者拒绝 |
| 引用校验 | 普通批次新增的引用查展示授权；恢复带回的引用只查历史登记，失效的照常恢复、显示占位 | 与 §3.3 原语义一致 |

**协同原则**（owner 2026-10-16，适用于画布、策划、场景）：Cmd+Z 只管自己的操作；历史版本列表和本轮改动清单可以明确地回退任何人的改动（「恢复这一处」保留）；助手总会被告知变化。策划的 `read_plan` / `write_plan` 要用底座修订列表的 `since_revision` 汇总「自你上次写入后的变化」，交给助手。

### 2.2 冲突单元

文档由以下冲突单元组成，每个单元有自己的 `rev`：

| 单元 | 内容 | 读者 |
|---|---|---|
| 标题 `meta`（底座保留单元） | 方案名 | 卡片、列表、历史 |
| 基本信息 `brief` | 作品、角色、版本/形态、拍摄形式（棚拍 / 外景 / 合成，可多选）、地点、约束 | 卡片、助手每轮开头、以后的发布到订单 |
| 每个章节 | `headline`（≤ 80 字）、`body`（Markdown）、`refs[]`、`not_applicable`；另有 `confirmed_rev`（§4.4） | 编辑视图、助手按章节读写 |
| 设定列表 `settings` | 设定的成员与顺序 | 编辑视图、卡片 |
| 每个设定 | `kind`、`name`、`notes`、`views[]`、`basis[]`；另有 `confirmed_rev` | 编辑视图、分镜生成、过时判断 |
| 镜头列表 `shots` | 镜头的成员与顺序 | 编辑视图、卡片镜头数 |
| 每个镜头 | `slot`、`framing`、文本字段、`setting_ids[]`、`storyboard`、`refs[]` | 编辑视图、以后的现场模式 |

- `slot` 是**交付用途**（`kv` 主视觉 / `half` 半身动态 / `closeup` 特写，由模板定义），`framing` 是**景别**（`full` / `half` / `closeup` / `other`）。新建镜头时 `framing` 默认取 slot 对应的景别，之后可独立修改。
- 字段借鉴旧 `shootplanning`：`brief` 对应 `CreativeBrief`，镜头文本字段对应 `Shot`。光向、光质、色调标签首版不做，写在 `lighting` 里。

### 2.3 图片与正文

- 图片只出现在 `refs[]` 和 `storyboard`，按内容修订引用，不引用画布节点。删除、替换画布上的图片节点不影响策划。
- 每个引用有稳定 `id`（`pref_` + UUID），由创建方生成，全文档唯一。
- **正文指代图片用引用标记** `[显示文字](ref:pref_…)`。标记绑定引用 ID，不绑定位置：编辑视图与导出把它渲染成「参考 3」这样的编号 chip，编号随当前顺序计算；排序、插入新图不改变所指。标记可以指向本文档任一章节或镜头的引用。
- 引用被删除后，标记渲染为「引用已删除」，不会顺延到下一张。写入时，本次写入的正文里如果出现文档中不存在的 `ref:` 标记，整次写入拒绝并说明是哪个标记（防止助手编造 ID）；未被本次写入的正文不复查。
- `source` 记录网上参考的出处（站点、作者、链接），由 V6-080 的取图工具或摄影师填写。

### 2.4 Markdown 子集

收：三级及以下标题、段落、有序 / 无序列表、任务列表（`- [ ]`，准备清单用）、加粗、斜体、引用块、链接、行内代码、`ref:` 引用标记。

不收：表格、HTML、图片语法、一二级标题、代码块。处理规则：

| 场景 | 处理 |
|---|---|
| 编辑器里粘贴富文本 | 能无损转换的直接转换（如一二级标题降为三级、HTML 加粗转 `**`）；表格转为每行一条列表项并提示「表格已转为列表」；粘贴图片时不插入，提示改用「添加参考图」 |
| 接口写入（助手或其他调用方） | 不支持的语法返回校验错误，指出位置与原因；**不静默剥除** |

### 2.5 不变量

- 章节由模板决定：章节 key 必须属于模板、不能增删、顺序固定。新文档创建时所有章节都在，内容为空。
- 引用 ID、镜头 ID 全文档唯一，格式为前缀 + UUID；重复 ID 拒绝。
- 字段语义：**缺省 = 不改；`null` = 清空**。只含空白的字符串归一为 `null`。数组字段（`refs`、`shoot_form`）给值即整体替换，`[]` 为清空。
- `storyboard.style` 取值 `sketch` / `grayscale` / `realistic` / `other`，为 V6-081 的风格选择预留。
- 镜头的 `setting_ids` 与分镜的 `based_on` 只能指向文档里存在的设定；删除设定时，引用它的镜头里一并移除该 ID（`based_on` 保留原记录，用于显示「设定已删除」）。
- 视角 `view` 取值：人设 `front` / `side` / `back` / `detail`，场景 `master` / `wide` / `reverse` / `detail`，另有 `other`。

### 2.6 上限

| 项 | 上限 |
|---|---|
| 单章正文 | 20,000 字 |
| 单章引用 / 单镜头引用 | 60 / 12 |
| 设定数 / 单个设定的视角图 | 12 / 8 |
| 镜头数 | 60 |
| 镜头单个文本字段 | 2,000 字 |
| 整份载荷编码后 | 512 KiB |

超限返回带说明的校验错误。

### 2.7 视觉设定与分镜一致性

分镜之间场景和角色要一致，后期才能复刻，所以分镜之前先定**视觉设定**（owner 2026-10-15）：

- **人设**（`kind: character`）：一般是三视图（正 / 侧 / 背），可加服装、道具细节图。策划阶段没有 coser 定妆照，人设图由助手基于搜集到的或摄影师提供的角色资料与图片生成。CP、团体时每个角色一份。`basis` 记录生成依据，指向文档里的引用（如官方立绘、设定集截图）。
- **场景**（`kind: scene`）：一张主场景图定下空间、陈设、材质和光线状态，其余角度（全景、反打、细节）由主场景图派生。合成片里，场景设定图同时是后期背景板的蓝本。
- 设定的确认规则与章节相同（§4.4）：只有摄影师能确认，之后任何修改都使确认失效。
- **镜头关联设定**：每个镜头用 `setting_ids` 指明用到哪些人设和场景。生成分镜时，助手把这些设定在画布上的节点连为分镜节点的上游参考（`generate_node` 只认上游连线），生成结果写进 `storyboard` 时一并记下 `based_on`（各设定当时的 `rev`）。
- **过时提示**：分镜 `based_on` 里任一设定的 `rev` 已不同于当前，或设定已删除，分镜显示「设定已更新」，可以一键交给助手重新生成。镜头没有关联设定时显示「未关联设定」。两种都只是提示，不阻止使用。
- **画布节点复用**：文档按内容修订记图，不记画布节点。生成分镜要连线时，助手先用 `read_canvas` 找当前显示该内容修订的图片节点，找到就复用，找不到才用 `add_node` 放上去。分镜同理：镜头已有分镜图时，重新生成（换构图、设定更新后重出）在显示它的那个节点上出新版本；只有在已有分镜上局部修改时，才按 `generate_node` 的规则新建节点并把原图连为参考。这样反复生成不会在画布上堆出重复的设定图和分镜节点。
- 这是首版唯一建立的跨章节依赖；其余章节之间仍只靠助手提醒复核（§6.5）。

## 3. 存储

### 3.1 迁移（编号接在底座 0069 之后）

通用的表和列（`creative_documents` 的时间、回收站、`unit_revs` 列，修订表、引用表、工作会话指针表）由底座迁移 0069 提供，见 `.lti/features/2026-10-16-creative-document-foundation/contracts.md` 的 `data: 通用文档`。策划只需要：

```sql
ALTER TABLE creative_contents DROP CONSTRAINT creative_contents_kind_check;
ALTER TABLE creative_contents ADD CONSTRAINT creative_contents_kind_check
  CHECK (kind IN ('text','link','image','video','audio','plan'));
```

- 回滚：内容类型约束退回前要求不存在 `plan` 内容，否则拒绝回滚。测试新增链头 `rollbackShootPlanDocument`，先回滚本迁移再调底座的 `rollbackDocumentFoundation`，并更新各迁移测试的标签列表。
- `changed_units` 的写法沿用（如 `meta`、`brief`、`section:lighting`、`shot:pshot_…`），确认操作记在 `annotated_units`。

### 3.2 内容层

- `creativecontent.Payload` 加 `Plan json.RawMessage`（`json:"plan,omitempty"`）。`Validate` 的 `plan` 分支只检查「只有 `plan` 字段」与 512 KiB 上限；结构由 `creativeplan` 在写入前校验。
- 每次保存调 `WriteAndRetain` 写一条新内容，历史顺序由 `creative_document_revisions` 承担。
- `plan` 不是媒体类型，不进 `IsMediaKind`。

### 3.3 GC、保留与可展示性

- 两张新表的 `content_revision_id` 加进 `LiveOwnerCondition`，在 `projection_roles_test.go` 登记为 `revisionHolder`。只要任一历史修订引用某张图，GC 就不回收它。
- 不回收只保证文件还在，不保证一定能展示：内容层还检查用途授权。读取时某张图不可展示，就在该位置显示「图片已不可用」占位，文档其余部分照常显示和编辑。
- 写入时只对**本次新加入**的引用做 `RequireUsable(…, "display")` 并要求是图片；已在文档中的引用不复查，所以一张图失效不会挡住其他修改。恢复含失效图片的旧版本照常允许，显示占位。
- 文档彻底删除时（§5.5）一并删除它的修订行与引用行，此后这些图片可被 GC 正常回收。

## 4. 写入与并发

### 4.1 命令

`POST /creative/documents/{id}/commands`，外壳由底座定义（§0.1）：沿用 `creativeops` 的 operation id 幂等与回执，一次请求是一组操作，全部成功或全部不生效，成功产生一个新修订。下表的「版本检查」即该操作涉及的单元；`rename`、`restore`、`restore_units` 是底座的通用操作，其余由 `creativeplan` 实现。

| 操作 | 参数 | 版本检查 | 谁能调 |
|---|---|---|---|
| `rename` | `title` | `meta`（底座） | 摄影师、助手 |
| `set_brief` | brief 字段 | `brief.rev` | 摄影师、助手 |
| `set_section` | `key`；`headline` / `body` / `refs` / `not_applicable` 任选 | 该章 `rev` | 摄影师、助手 |
| `confirm_section` | `key` | 该章 `rev`；标注操作，不推进 `rev` | 仅摄影师 |
| `unconfirm_section` | `key` | 不检查；标注操作 | 仅摄影师 |
| `add_shot` | `shot_id`、`slot`、`after_id`（可空）、字段 | `shots.rev` | 摄影师、助手 |
| `update_shot` | `shot_id`、字段 | 该镜头 `rev` | 摄影师、助手 |
| `move_shot` | `shot_id`、`slot`、`after_id` | `shots.rev` | 摄影师、助手 |
| `remove_shot` | `shot_id` | `shots.rev` **且**该镜头 `rev` | 摄影师、助手 |
| `add_setting` | `setting_id`、`kind`、`name`、`after_id`、字段 | `settings.rev` | 摄影师、助手 |
| `update_setting` | `setting_id`、`name` / `notes` / `views` / `basis` 任选 | 该设定 `rev` | 摄影师、助手 |
| `remove_setting` | `setting_id` | `settings.rev` **且**该设定 `rev` | 摄影师、助手 |
| `confirm_setting` / `unconfirm_setting` | `setting_id` | 该设定 `rev` / 不检查；标注操作 | 仅摄影师 |
| `restore` | `revision`（要恢复的旧修订号），请求带 `expected_revision` | 文档修订号（底座）；**必须单独成批** | 仅摄影师 |
| `restore_units` | `units`（`changed_units` 写法，可多个）、`from_revision` | 列出的单元；镜头 / 设定在旧修订里不存在或现在不存在时另查 `shots` / `settings`（底座的集合单元规则）；当前不存在的单元预期写 null；**必须单独成批** | 摄影师、助手 |

- 删除镜头同时检查列表与镜头本身：助手刚改完镜头 A，摄影师基于旧内容删除 A 会冲突，而不是悄悄删掉新内容。移动不丢正文，只检查列表。
- 节点改名、编辑器改名、助手改名都走 `rename`，统一进入历史与回执（§5.1）。
- 回收站与彻底删除是独立接口（§5.5），不在命令里。
- `restore_units` 把列出的单元改回旧修订 k 里的样子，其余单元不动，产生新修订 N+1，这些单元的 `rev` 设为 N+1（下文与 §7.7 中的「恢复这一处」即只列一个单元的 `restore_units`）：
  - 镜头在 k 里不存在（是之后新增的）则删除；现在不存在而 k 里有则加回原位置。
  - 若该单元在 k 里处于「已确认」（`confirmed_rev` 等于修订 k 的 `unit_revs` 中该单元的值），恢复后仍为已确认，`confirmed_rev` 设为 N+1，因为内容正是当时被确认的那一份；否则确认状态按 §4.4 照常失效。
  - 修订记 `restored_from = k` 与该单元，供改动清单判断「已恢复」（§7.7）。

### 4.2 版本令牌

> 2026-10-16：本节规则由底座统一实现（单元修订号存于 `unit_revs`；整份恢复带 `expected_revision`；冲突详情只列单元与修订号，客户端重读后进入冲突界面）。以下保留为策划视角的说明。

- **单元的 `rev` = 该单元最后一次被改动时的文档修订号。** 文档修订号单调递增、永不复用，所以任何单元的 `rev` 都不会回退或重复。
- 成功写入产生文档修订 N+1：被改动的单元 `rev` 设为 N+1，其余不变。`shots.rev` 只在增、删、移动时更新；改单个镜头只更新该镜头。
- 同一请求里每个冲突单元最多一个操作（重复拒绝）；所有检查都对照请求前的状态。客户端要把同一章节的正文、引用等合并成一个 `set_section`。
- 冲突返回 409 `creative_document_conflict`，附冲突单元的最新内容与 `rev`；不做文本级自动合并，合并由摄影师在冲突界面编辑完成（§7.3 第 6 条）。
- **恢复**：读出旧修订 k 的载荷，存成新修订 N+1，**所有单元（含标题、设定列表、每个设定、镜头列表、每个镜头）的 `rev` 一律设为 N+1**，包括恢复后重新出现的镜头。效果：恢复之前发出的任何请求都会冲突，持有旧令牌的编辑器全部失效。旧版本里处于「已确认」的章节（`confirmed_rev == rev`）恢复后仍为已确认（`confirmed_rev` 同步设为 N+1），因为内容正是当时被确认的那一份。`restored_from` 记 k。

### 4.3 写入流程

服务端在文档行锁内：读当前快照 → 逐个检查版本 → 应用操作并校验不变量 → 写新内容修订、修订行、引用行 → 更新 `creative_documents` 的 `revision`、`content_revision_id`、`title`、`updated_at`。回收站中的文档拒绝写入。

### 4.4 确认与状态

- 「已确认」表示**摄影师审核过这一版内容**：`confirm_section` 把 `confirmed_rev` 设为当前 `rev`，本身不改 `rev`。
- 显示状态由数据派生，不另存：

| 状态 | 条件 |
|---|---|
| 本次不适用 | `not_applicable = true` |
| 空 | 正文、`headline`、引用都为空 |
| 已确认 | `confirmed_rev == rev` |
| 确认后有修改 | 有 `confirmed_rev` 但不等于 `rev` |
| 草稿 | 其余 |

- 任何人修改正文、引用、`headline` 或「不适用」都会推进 `rev`，确认随之失效，卡片显示「确认后有修改」，摄影师一键重新确认即可。
- 助手不能确认：即使摄影师在对话里说「可以」，助手写入后的内容仍需摄影师在编辑视图确认。这样「已确认」始终对应摄影师看过的那一版。
- 「本次不适用」摄影师和助手都能设置（例如外景实拍不需要后期合成），它是内容判断，可随时改回。

### 4.5 修订记录

每个修订记 `actor_kind`、`run_id`、`changed_units`。历史列表显示「你 / 助手（对话名）· 时间 · 改了哪些部分」。

这三项同时支撑 §7.7 的对照：
- 「自确认以来」：对照版本取 `confirmed_rev` 那一版里的该单元。
- 「本轮改了什么」：本轮写过的单元来自 `run_id` 相同的修订的 `changed_units`；每个单元的对照版本取它在本轮第一次被写之前那一版。

## 5. 画布节点

### 5.1 节点定义

```go
{TypeKey: "photo.shoot_plan", SchemaVersion: 1, CreationSupported: true,
 EditableFields: []string{"placement"}, Ports: []string{},
 Actions: []string{"move", "resize", "rename", "remove", "maximize"},
 PromptMode: "unavailable", Maximize: true}
```

- 摄影业务扩展用 `photo.*` 命名空间。
- 不带端口、不带 `duplicate`、不带 `save_to_library`。
- **改名**：节点上的改名入口调用文档命令 `rename`，不走画布的 `update_metadata`；节点标签显示文档标题。助手用 `edit_canvas` 改策划节点标题会被拒绝，提示改用 `write_plan` 的 `rename`。
- 默认尺寸 360 × 300。

### 5.2 创建与放回

- **新建**：`add_node` 带 `type_key: "photo.shoot_plan"`、`template_key`（策划类型，首版只接受 `cosplay-sop`）与可选 `title`。同一事务里由文档类型端口（§5.4）生成空白载荷，写内容、`creative_documents` 行、第 1 个修订行，再落节点。撤销这次画布改动只移除节点，文档留下，可从「引用已有策划」找回。
- **放回已有策划**：`add_node` 带 `document_id`（与内容、素材互斥）。工具栏「+」与右键菜单加「引用已有策划」，选择框按最近修改列出本账号策划，可按标题搜索；回收站中的不列出。
- 一份策划可以出现在多张画布上，都是同一文档的入口。删除节点不删除文档。

### 5.3 卡片摘要

节点快照为 `photo.shoot_plan` 返回 `document_summary`，由 `creativeplan` 从当前修订算出：

| 字段 | 来源 |
|---|---|
| `title` | 当前标题 |
| `subtitle` | `brief.work · brief.character（variant）` |
| `headline` | 「创意方向」的 `headline`，为空时取第一个非空章节的 `headline` |
| `cover_refs` | 最多 3 张：优先 KV 镜头的分镜图，其次场景设定主图，再次情绪板引用；不可展示的跳过 |
| `stale_storyboards` | 显示「设定已更新」的分镜数，大于 0 时卡片上提示 |
| `shot_counts` | 按 `slot` 计数，附模板目标数（如 KV 2/2） |
| `shot_progress` | `planned`（动作、构图、光线都已填写的镜头数）、`boards_ready`（有分镜图且不过时）、`target`（模板目标总数）；卡片显示「已规划 x/9 · 分镜图 y/9」 |
| `sections` | 每章 `key` 与派生状态，卡片画成一排状态点 |
| `trashed` | 是否在回收站 |
| `revision`、`updated_at` | 当前修订 |

文档在回收站时卡片显示「策划在回收站」并提供恢复；被彻底删除时节点标 `Unavailable`（沿用现有处理），只能移除。

### 5.4 文档类型端口

> 2026-10-16：改用底座的 `creativedocument.Type`（§0.1），下面的接口草稿作废，仅保留「`creativecanvas` 不 import `creativeplan`」与「未注册的类型可读不可新建」两条约定。

`creativecanvas` 不 import `creativeplan`。在组合根注册：

```go
type DocumentType interface {
    TypeKey() string                              // "photo.shoot_plan"
    Empty(title string) (json.RawMessage, error)  // 新建时的空白载荷
    Summary(ctx context.Context, tx store.TxAccountScope, payload json.RawMessage) (json.RawMessage, error)
}
```

`creativeplan` 实现它，同时提供命令、读取和助手工具。未注册的文档类型照常可读、不能新建。

### 5.5 回收站与彻底删除

- `POST /creative/documents/{id}/trash`、`/untrash`：设置或清除 `trashed_at`。回收站中的文档可读、不可写，不出现在「引用已有策划」里；选择框有「回收站」分页，可恢复。
- `POST /creative/documents/{id}/purge`（底座，2026-10-16 由 `DELETE` 改为标准命令封套）：只允许删除回收站中的文档，删除文档行、修订行、引用行与工作会话指针（会话本身保留）；指向它的节点变为不可用。删除前确认框写明「历史版本一并删除，不可恢复」。
- 只有摄影师能操作；助手没有对应工具。
- 首版不做到期自动清理回收站，也不做单个历史版本的清理。

`readableRevisionInTx` 加一条：内容修订被**当前画布上某个策划节点所指文档的当前修订**引用时可读。

### 6.5 工具说明

写清：生成分镜前先确认镜头关联的设定已确认，并把设定节点连为上游参考，写回分镜时带上 `based_on`；按章节写、冲突时重读、图片放 `refs` 并用 `ref:` 标记指代、助手不能确认章节、改动一个章节后提醒摄影师复核可能受影响的章节（如创意方向变了，灯光和分镜可能过时）。首版不建章节依赖关系，跨章节一致性靠这条提醒；完整流程规则归 V6-081 的 Skill。另写清：
- **按需读**：不规定每轮先读。要改哪一处先读那一处（用 `sections` 只读这一章）；回答涉及策划内容时以本轮读到的为准，历史里的读取结果可能已经过时；打招呼、处理与策划无关的任务时不读。写入有版本令牌兜底，基于过时内容的写入会冲突，不会覆盖摄影师的修改。
- 消息里带 `document_ref` 时，先用 `read_plan` 读它指向的单元再动手（§7.6）。带 `quote` 时只改摘录所在的那一段，带 `ref_id` 时按那张参考图改，其余内容原样保留，不整章重写。
- 一轮写完后，在回复里说清改了哪几处、哪些已确认的内容没有动；改动清单由界面从修订记录生成，不需要助手自己列表格。
- 「补齐镜头方案」和「生成分镜图」是两件事：前者只写镜头文字，后者先按 V6-081 的规则停下来确认范围、风格、模型和消耗。
- 生成分镜时复用画布上已有的设定图与分镜节点（§2.7），不重复放图。
- **分镜写回冲突**：生成要等一段时间，期间摄影师可能改了这个镜头。`update_shot` 冲突时重读，用最新 `rev` 只写 `storyboard`，不带文字字段，摄影师刚改的文字原样保留；镜头已被删除时如实告诉摄影师，图仍在画布上。

### 6.6 Skill 加载

> 2026-10-15 实现修订：Skill 运行时已按 [Agent Skills 与 Tools 运行契约](../../../docs/dev/agent-skills-tools.md) 改造。「平台内置 Skill 进索引」由每轮的 Skill 目录摘要（平台与账号自己的 Skill，另有 `search_skills`）实现，账号自己的 Skill 也会出现；「加载一次、之后几轮不重复加载」由跨轮沿用激活实现，版本停用时不再发送历史正文。下文其余约定不变。

不给每条消息挂 Skill：消息上挂的 Skill，正文只进那一轮，每轮都要重付一份，打招呼也一样。改为**需要时加载一次，留在上下文里**：`load_skill` 的结果本来就留在历史中，后面几轮都能用，压缩后摘要会提示按原版本重新加载。

现在 `load_skill` 只能加载本会话用过的 Skill，助手没法主动加载一个从没出现过的 Skill，所以补两处：

- **平台内置 Skill 进索引**：创建运行时，把当前可用的平台内置 Skill（名称、一句话说明、固定的版本 ID）冻结进本轮的 Skill 索引，和「本会话用过的」并列。运行中仍然不查目录、不解析最新指针，沿用现有原则。工具未注册而不可用的 Skill 不进索引。账号自己发布的 Skill 不进，仍由摄影师手动挂标签。
- **base 指令只写通用规则**：要做的事有对应的 Skill 时先加载；已加载且仍在上下文里的不重复加载；打招呼、闲聊不加载。不在 base 指令里点名某个 Skill，以后加婚纱、写真模板也不用改。
- **碰到策划时给确定的提示**：模板声明配套 Skill（`cosplay-sop` → cosplay 拍摄策划 Skill）。`read_plan`、`read_canvas` 读到策划时，结果里带上配套 Skill 的名称与 `skill_version_id`，并说明是否已加载。「已加载」指本轮挂着这个 Skill，或本轮上下文（冻结的历史与本轮已有的步骤）里有它的 `load_skill` 结果；没加载时附一句「本策划配套 Skill「X」尚未加载，先 `load_skill` 再按其中方法操作」。配套 Skill 不可用时不带这一项，也不提示。

摄影师手动挂 Skill 标签仍然可用，用于强制带上；编辑视图不再默认挂。`load_skill` 只提供方法，不增加本轮可用的工具，`read_plan` / `write_plan` 本来就按部署能力开放。

## 7. 编辑视图

### 7.1 布局

双击节点或点「最大化」进入，替换现有只读 `DocumentView`：

- **左栏**：章节目录，每章一个状态点（空 / 草稿 / 已确认 / 确认后有修改 / 不适用）和章节名，点击滚动定位；每个条目的可访问名称为「章节名 · 状态」。
  - 窗口窄于 1100px 时左栏收起，顶栏出现「目录 · 当前章节名」按钮，展开为带状态的章节菜单。不做只剩状态点的窄栏。

- **主区**：基本信息表单 → 各章节 → 镜头表。

  - 视觉设定：人设与场景两组卡片。每张卡片是设定名、状态与确认、多视角大图（标注正 / 侧 / 背或主场景 / 反打等）、说明与生成依据；可「添加人设」「添加场景」「让助手生成设定」。
  - 镜头表：按 KV / 半身 / 特写分组并显示目标数；每个镜头一张卡片：分镜图位（「添加分镜图」）、关联的设定 chip、景别、文本字段、参考缩略图；分镜过时时图上显示「设定已更新 · 重新生成」。
    - **完成度分开算**：「已规划 x / 9」（动作、构图、光线都填了才算，缺的在卡片上标「待补 构图、光线」）、「分镜图可用 y / 9」（有图且不过时）、「z 张基于旧设定」。卡片摘要同样给前两个数，不再只给镜头数量。
    - **两种视图**：逐张卡片用于精修；紧凑总览按 2 + 4 + 3 一屏排开，每格是分镜图、编号、标题、动作，空位显示「待补」，用来比较整组的动作、构图和情绪是否重复或递进，点一格回到卡片视图并定位。
    - **两个助手入口**：「补齐镜头方案」只写镜头文字（补空字段、补到目标数），不生成图；「生成分镜图」先进入选择：卡片和总览格子上出现勾选框，默认勾上没有图的和基于旧设定的，底部操作条显示已选数量与风格，「交给助手」起草一条带这些镜头标签和风格的消息。发送后助手按 V6-081 先列出目标镜头、参考连线、模型参数和预计消耗，摄影师确认后才生成。
- 空章节显示模板提示（来自 SOP 子项）。

### 7.2 添加参考图

每个参考图组和分镜位都有「添加参考图」，打开选择器，两个分页：

- **当前画布**：列出当前画布的图片节点，取节点**当前显示版本**的内容修订。数据来自已加载的画布快照，不用退出编辑视图。
- **资产库**：复用 `LibraryPicker`，取素材当前修订。

可以多选，一次加入，选择后可直接填写说明。拖拽只作为补充：资产库选择器里可以把图拖进分组。首版不支持从电脑上传，选择器里提示「先放到画布或资产库」。

### 7.3 保存状态机

**冲突单元**（§2.2）是保存的最小单位，每个单元在前端有一份状态：

| 状态 | 含义 |
|---|---|
| `clean` | 与服务端一致 |
| `dirty` | 有本地修改未发出 |
| `saving` | 一个请求在途，请求体与 operation id 已固定 |
| `conflict` | 收到 409，等摄影师选择 |

规则：

1. **同一单元串行**：一个单元同时最多一个请求在途；在途期间的新修改累积为待提交草稿，回包后再合并成下一个请求。不同单元可以并发保存。
2. **触发**：正文停止输入 1.5 秒或失焦时提交；表单字段、引用、镜头操作即时提交（仍受规则 1 约束）。同一章节的正文和引用合并进一个 `set_section`。
3. **重试不改请求体**：网络失败时用同一 operation id、同一请求体重试，指数退避；界面显示「未保存，重试中」。
4. **回包只确认已发出的内容**：成功后单元的基准 `rev` 更新为回包里的新 `rev`；若在途期间有新输入，状态回到 `dirty`，不清掉新输入。
5. **服务端推送**：收到画布失效后重读文档。`clean` 单元直接采用服务端内容；`dirty` / `saving` / `conflict` 单元保留本地内容，不覆盖。自己保存引起的推送，重读后 `rev` 与基准一致，无变化。
6. **冲突处理**：单元顶部提示「这一部分刚被助手（或另一个窗口）修改」，并排显示两边各改了什么，三个选择：
   - 「用新的版本」：丢弃本地，采用服务端内容。
   - 「保留我的」：以本地内容、**冲突回包里的最新 `rev`** 重新提交；若这期间又被改动，再次进入冲突，不做无条件覆盖。
   - 「合并后保存」：对照区下方出现可编辑的最终内容（先填入本地版本），摄影师把对方合理的改动写进去；参考图把两边的并集逐张列出，标明「两边都有 / 只在你的版本 / 助手新加」，逐张勾选保留。保存时同样用冲突回包里的最新 `rev`，规则同上。两边改的是不同段落时也不自动合并，只在对照里标出来。
7. **本机留存**：`dirty` / `saving` / `conflict` 单元的内容连同基准 `rev` 写入浏览器本地存储（读写失败不影响编辑）。重新打开文档时，**界面显示本机内容而不是服务端旧内容**，顶栏显示「未保存 · 内容在本机」：服务端 `rev` 仍等于基准，恢复为 `dirty` 并提交；已变化则进入 `conflict`。不允许出现「顶栏说未保存、字段却是空的」这种状态。
8. **离开**：关闭编辑视图、切换文档时，先尝试提交 `dirty` 单元并等待在途请求最多 3 秒；仍未完成则保留本机留存并提示「有内容尚未保存，下次打开时继续」。刷新或关闭页面时有未保存内容，弹浏览器离开确认。

编辑器内的 ⌘Z 只作用于正在输入的文字；更大范围的回退走「历史版本」。编辑视图打开时画布快捷键不生效。

### 7.4 实时

文档写入会更新 `creative_documents` 行，0042 触发器让同账号画布流失效；编辑视图与卡片据此重读（规则见 §7.3 第 5 条）。

### 7.5 历史版本

「看改动」与改动清单（§7.7）是查看改动的第一入口，历史抽屉是第二层：用于找更早的版本或整份恢复。右侧抽屉按时间倒序列出修订：谁、何时、改了哪些部分。点开只读预览（不可展示的图显示占位），可「恢复到这个版本」：产生新修订，不删除之后的历史；恢复前若有未保存的本地修改，先提示处理。

### 7.6 助手面板与工作会话

策划界面里的助手就是画布助手面板里的一个会话，不另做章节级 AI。策划靠多轮决策累积（选了哪个方向、否掉了哪张参考、为什么），这些只在对话里出现过；另开一个上下文的助手改章节时看不到它们，写出来会和前面的讨论矛盾。两套上下文还会带来两套写入槽和两套消耗。

- **同一个组件、同一份面板状态**：编辑视图右栏复用 `AgentPanel`。摄影师不一定只在策划里操作助手，画布面板和编辑视图里的面板必须相通，所以「当前会话、输入框草稿、运行状态、面板开合」是画布页面上的一份状态（从 `AgentPanel` 内部提到画布编辑器层），两处只是两个显示位置：
  - 在编辑视图里发的消息、助手的回复，回到画布后在面板里是同一串，反过来也一样。
  - 画布上开着助手面板时，打开策划，编辑视图右栏直接显示助手；关闭策划回到画布，面板仍停在同一个会话、草稿还在。
  - 在画布面板里发起、让助手改了策划的运行，节点卡片和打开着的编辑视图都按 §7.4 刷新；编辑视图里发起的运行，画布面板也显示在跑。
  - 画布面板的 `@` 可以选画布上的策划节点，发出去是指向整份文档的 `document_ref`；对话里的策划标签在画布上点击时打开策划并定位。
- **入口只起草消息**：这些入口都不直接发起运行，而是打开助手面板，附上指向这一处的标签。摄影师补一句要求再发送（如「保留顶光方向，只把三灯压成两灯」），所有操作都留在对话里，后面的轮次看得到。入口包括：
  - 章节头的「请助手修改」：输入框留空，提示示例要求，不预填「重写这一章」。
  - 正文或镜头字段里选中一段文字：浮出「请助手修改这段」，标签带上摘录（如「@后期合成 · “抠像：发丝…”」）。
  - 参考图菜单的「请助手按这张图修改」：标签带上图的编号。
  - 镜头菜单的「请助手修改这个镜头」「重新生成分镜图」。
  - 视觉设定的「让助手生成设定」。

  助手写完后，正文保持可见；回复里的标签和改动清单（§7.7）点击即定位到结果。
- **`document_ref` 片段**：提交协议新增 `{type: "document_ref", document_id, unit?, quote?, ref_id?}`：
  - `unit` 用 `changed_units` 的写法（如 `section:lighting`、`setting:pset_…`、`shot:pshot_…`），不给表示整份文档。
  - `quote` 是选中的原文摘录，≤ 200 字；`ref_id` 是该单元里某张参考图的引用 ID。两者都只是指引：摘录找不到（期间被改过）时，助手按单元处理并说明。服务端核对文档属于本账号、在回收站外、且在会话所在画布上有节点；消息里显示为标签。它只是指引，不授予额外读取权限，助手仍通过 `read_plan` 读内容。
- **工作会话**：`creative_document_conversations` 按「文档 + 画布」记一个会话。
  - **打开策划不切换会话**：面板已经有当前会话时，编辑视图沿用它，不打断正在进行的对话；如果它不是这份策划的工作会话，面板顶部提示「这份策划之前在『X』里讨论 · 切过去」，由摄影师决定。
  - 面板还没有当前会话时（如刚进入画布），打开编辑视图里的助手直接进入这份策划的工作会话；没有或已被删除时，新建会话，标题为「<类型名> · <策划标题>」（如「拍摄策划 · 芙宁娜」），并记为工作会话。
  - 从编辑视图发消息、在任何位置发出带这份策划 `document_ref` 的消息、或助手 `write_plan` 写入这份文档时，把当时的会话记为当前画布上的工作会话。
  - 同一画布上有多份策划时，默认各用各的会话。一份策划在多张画布上时，每张画布各有自己的工作会话，因为运行能动的画布由会话决定。
- **不默认挂 Skill**：编辑视图和 `@` 了策划时，输入框都不自动带 Skill 标签。助手第一次操作策划时自行加载模板配套的 Skill，之后几轮不再重复加载（§6.6）；摄影师仍可在 `@` 菜单里手动带上。
- **连续性分三层**：会话负责最近的讨论与取舍理由；策划文档负责已定下的内容（确认过的章节、设定、引用），助手要动哪一处就先读哪一处，所以会话压缩或换会话后不丢进度；画布负责图。
- 运行状态沿用现有面板：写入槽被占时排队；助手写某一章时，该章显示「助手正在写这一章」（来自运行事件里的 `write_plan` 调用）。

### 7.7 看改动与本轮审核

助手直接写入，不设「先提议、摄影师逐条批准后才落地」的建议层：那会给助手加一道写入闸门，多处联动修改会很慢，文档里还要同时存一份待定内容，冲突和保存规则都得重做。改为**先写入、后审核**，靠下面两个入口让复核成本足够低：

- **「看改动」在原位展开**：章节或设定处于「确认后有修改」时，点「看改动」在这一处下方展开对照面板，显示自确认版本以来改了什么，历史抽屉退到第二层。面板里：
  - 一句话概括与镜头、设定等短字段逐项对比，删去的划线变灰，新增的提亮底色。不用红绿，沿用中性色加单一锚点色。
  - 正文按段落对齐：未改动的段落折叠成「N 段未改动」并保留小标题定位；一段被改时标出字符级差别；整段新增或删除单独标出。
  - 参考图、设定图、分镜图按 ID 列出新增和去掉的缩略图。
  - 操作：「看过了，重新确认」、「恢复到确认时的内容」（`restore_units`，恢复后仍为已确认）、「在历史版本里看」。
- **本轮改动清单**：一轮运行写过策划后，对话里在助手回复下方出现「本轮改了 N 处」卡片，数据来自本轮修订的 `changed_units`（§4.5）。每处一行：
  - 状态：待确认 / 已确认（章节、设定），待看 / 看过了（基本信息、镜头），已恢复。前两类与「已恢复」从文档与修订记录派生；「看过了」只记在本机浏览器，不入库。
  - 「看改动」：打开策划并定位到这一处，展开「本轮之前 → 现在」的对照，操作是「确认」或「看过了」，以及「恢复这一处」（`restore_units` 到本轮之前那一版）。
  - 卡片在画布面板和编辑视图里一样可用；点击时编辑视图没开就先打开。
- 这样「棚拍只剩两小时、两盏灯、不能洒水」这类要求一次改动多处时，摄影师逐处看、确认或恢复，不用自己翻历史版本找差别。整轮一键撤销仍随 V6-038。

## 12. 遗留风险

- **复制画布 / 模板（V6-050 / V6-065）**：复制含策划节点的画布时，指向同一文档还是复制一份，由那两条在设计时决定。
- **归档项目**：文档独立于项目，后端不随项目归档变只读；从归档项目打开时，前端以只读方式显示。
- **助手「撤销本轮」**：本期可在改动清单里按单元恢复（§7.7）；整轮一键撤销随 V6-038。
- **段落对齐的对照**：按段落文字对齐，段落被拆分或合并时会显示成一删一增；够用就不做更细的结构对齐。
- **跨章节一致性**：只靠助手提醒复核，不做依赖追踪；若走查中经常出现过时章节，再考虑「上游已变」标记。
- **Skill 是否被加载**：靠助手按索引自行加载，读到策划时的提示兜底。走查中若仍常漏加载，再考虑对带 `document_ref` 的消息由服务端直接挂上配套 Skill。
- **载荷整份存储**：频繁编辑会积累修订行，单份上限 512 KiB，首版不压缩、不清理。
