# V6-008 验证记录

> **v2 返工（2026-10-08）** 见文末「v2 验证」。v2 取代了 v1 的「上传完成由服务端绑定节点」：上传改为暂存，填入节点改为用户编辑 `fill_from_upload`。下面 v1 的部分保留作历史记录；凡与 v2 冲突的，以 v2 为准。

设计：[batch-file-import-undo-design.md](batch-file-import-undo-design.md)。前后端都有改动，契约只多了一个可选字段。

## 实现取舍

- 填充单个空节点不使用撤销组。这一步的 bind 本身就是一条普通 change，撤销后节点回到空的状态。design 里原本写的「单独建一个组」没有必要，已经简化掉。代价是：单个节点的填充还在上传时按撤销，不会取消这个上传。上传完成时节点已经变了，结果会落成候选，界面上仍然显示原来的「目标已变化，待处理」提示。批量导入不受这个影响。
- 组被别的改动隔开时（比如上传还没完成就拖动了节点），撤销退回到逐条撤销。原因是服务器按组撤销会把组里的所有改动一起回退，跨过中间那条改动就不对了。
- 撤销时如果取消没赶上（会话已经进入发布），前端会等这个会话结束：已经绑定的内容随撤销组一起回退；落成候选的，直接调用 discard 放弃，不提示。
- 拖进来但没有建节点的文件（格式不支持、超出数量）会出现在托盘里，逐项写明原因，并且不提供重试，因为没有目标节点。

## v2 验证（本地预览 + 画布只由用户编辑改动）

设计见 design §6。

### 实现取舍

- 新建包 `creativestaging`，负责暂存上传，复用 `creative_upload_candidates` 表（`reason='staged'`）。media worker 写入暂存，canvas 在 batch 里消耗，避免 canvas 和 media 互相 import。暂存不出现在候选列表里，绑定状态显示为 `staged`。
- `fill_from_upload` 是普通的画布动作，暂存只能用一次。如果暂存已被放弃、过期或用过，返回 `ErrVersionConflict`，这次编辑不提交。
- 前端：
  - 拖入后立刻用 blob URL 显示内容，变暗、转圈，并显示进度。
  - 图片和视频在本机读出尺寸，节点高度先按比例算好。
  - 服务端内容加载出来之后，才撤掉本机预览。
- 撤销：
  - 一批导入里本机还没发出的部分（建节点、已入队的填充）一起撤回。
  - 已经发出的部分按组交给服务器撤销。
  - 已经入队填充的上传不会被放弃暂存，否则正在发送的填充会撞上「已放弃」而冲突。这个问题是 e2e 在「填充与撤销同时进行」的时序里抓出来的。
- 单个空节点的填充也走暂存加填充这条路。上传期间按撤销就会取消这次上传，撤销按钮在这时可用；如果这次上传之后又有别的编辑，撤销先撤那个编辑。v1 的已知缺口已经补上。
- 建上传会话的请求不随撤销中止：先拿到会话，再取消，不会留下占着额度的孤儿会话。
- 迁移 0055 放开了 `creative_uploads.target_kind` 的 `staged`。如果还有暂存上传，回滚会拒绝。store 的回滚链测试都已加上这一步。

### 修复：撤销后节点先变空、过一会儿才消失（owner 测试发现，2026-10-08）

- **原因**：撤销意图本身没有本机投影，节点要等服务器的撤销回执（发送延迟 250ms，再加一次往返）才会从画布上去掉。但撤销时本机预览已经立刻清掉了，所以这段时间里节点显示成「空节点」。
- **修复**：撤销一批导入时，撤销意图带上 `hides`（这一批新建的节点）；撤销单节点填充时带上 `empties`。`projectCanvas` 会在本机立即画出撤销结果，不等回执。如果服务器拒绝，意图会被丢弃，节点自然回来。为了不误画，只有确定这次撤销会撤掉整批时才提前画：判断条件是导入之后除了它自己的填充，没有插入别的编辑。
- **证据**：新增 e2e 记录 `AC-02 instant`。把撤销请求扣在服务器端，节点在 1.5 秒内消失，期间每一帧都没有渲染过空节点；回执到达后节点也不会回来。去掉提前绘制后，这条记录失败。现在 `creative-file-import` 共 8 个记录，连续跑 3 次都通过。
