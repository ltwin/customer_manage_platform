# 摄影师创作系统：四支柱远期形态

> 创意空间 | 2026-09-04 创建 | 上游：`.codestable/epics/creative-workspace-redesign.md`（先导版）、`.codestable/brainstorms/creative-shoot-planning/brainstorm.md`（旧立项判断）| 下一步：等先导 `pilot-evidence-go` 出结果，再决定知识库 + Agent 是否立项

## 出发点

`creative-workspace-redesign` Epic 把旧策划系统收缩成一个可部署的先导版：批量搬入、图片优先灵感墙、显式拍摄项、图优先现场模式。评审时出现一个自然的疑问：初版看起来像一个高级收藏夹，它和 owner 早已提出的「画布节点 + AI 一键产出策划与分镜 + 垂类知识库」愿景能不能接上？

owner 的回答把这个疑问变成了定位：**灵感墙不是收藏夹，是资源库；画布不是更大的灵感墙，是创作系统；知识库在本质上也是资源库。** 由此远期形态定为四支柱：

| 支柱 | 角色 | 谁写入 | 谁读取 |
|---|---|---|---|
| 资源库 | 摄影师自己攒下的图片、文字、链接，先导版的灵感墙即其第一形态 | 摄影师 | 摄影师、Agent |
| 知识库 | 垂类作品与角色的事实、视觉约束，解决通用 LLM 对冷门番剧 / 游戏理解不足 | 平台运营（内置）、摄影师（账号私有） | 主要是 Agent |
| Agent 助手 | 以资源库 + 知识库 + 本次拍摄约束为输入，产出可追溯、可编辑的候选（策划案、拍摄项、分镜） | — | 摄影师 |
| 画布节点 | 摄影师与 Agent 共同组合资源的工作面，图片 / 视频 / 文本节点自由组合与连线 | 摄影师、Agent | 摄影师 |

这份 brainstorm 只固化定位、依赖关系与建设顺序，不是任何一项的立项文件。四支柱中除资源库外，其余三项都在先导 Epic 的「证据门后候选」，只有 `pilot-evidence-go` 给出结果后才分别评估。

## 聊过的方向

### 先导版验证的是资源层，不是收藏夹好不好用

四支柱的依赖关系是单向的：Agent 没有资源库和知识库就没有输入，画布没有 Agent 就只是一块更重的手工整理面，而 owner 自己的反馈恰恰是嫌旧系统重。所以资源层是整套系统的地基，先导 pilot 回答的真正问题是「摄影师会不会主动把资源放进来」，而不是「这个网格比小红书收藏夹强多少」。

这个定位顺带修正了先导 Epic 对失败形态的解读：「素材堆积但策展不发生」在四支柱框架下不是失败，而是资源层已成、创作层待建的正常状态，正是 Agent 该介入的信号。先导 Epic 已把它记为具名 disposition `manual-curation-too-costly`。

### 知识库与资源库同构，但不合表

两者在存储形状上确实同构：都是带来源分类、带权利声明的图文材料。共享的基础已经存在——旧实现 `backend/internal/planningmedia/matrix.go` 的来源分类已区分官方、番剧截图、设定集、同人、未知网络、摄影师自有、授权、客户提供，`generation_reference` 用途 fail-closed 且需显式 grant。这套矩阵是两者共同的权利地基。

不同的是三件事，足以否决「现在就建通用资产抽象合成一张表」：

- **写入者不同**：资源库是摄影师写给自己的；内置知识库由平台运营维护，账号私有知识库由摄影师为 Agent 补充。
- **读取者不同**：资源库给人逛，需要网格与排序；知识库给 Agent 检索，需要索引与溯源，人几乎不直接浏览。
- **权利边界不同**：内置知识库若由平台提供番剧截图与设定集，作为云端 SaaS 有 IP 暴露；账号私有知识库由摄影师自担来源，风险面完全不同。

结论：概念上同属「资源」，工程上只共享权利矩阵与媒体身份，各自的表在各自立项时再建。先导 Epic 已把「不建通用资产抽象合表」写进非目标。

### 画布的两种身份，只有一种值得先做

画布可以是摄影师的**输入工具**（自己拖节点、连线、表达素材关系），也可以是 Agent 的**输出呈现面**（策划案与分镜以节点图形式展开，摄影师在上面改）。TapNow 式产品里画布主要是后者。

判断：作为输入工具的画布，只有 pilot 明确出现「我需要表达素材之间的关系」的真实摩擦才立项；作为输出呈现面的画布，与 Agent 一并评估。两种身份都不该在 Agent 之前建，理由是先导 Epic 遗留风险 12 已指出的方向冲突：画布 + AI 主张「不必自己整理」，而摄影师嫌重的正是手工整理。

### Agent 的第一版不需要画布

更便宜的路径是让 Agent 的输出直接落成**候选卡片**和**候选拍摄项**，由先导版已有的灵感墙与拍摄清单承接。这样「AI 整理有没有价值」这个问题可以在不建画布的情况下得到回答，且沿用旧 brainstorm 已拍板的先导指标——**采用率**：AI 产出的候选中被写入拍摄清单且现场被完成的比例。

旧 `creative-shoot-intelligence` roadmap 里「先做缺口检查、不做生成」的顺序仍然成立，但输入形态变了：旧方案的输入是结构化 shot list，新方案的输入是资源库里未结构化的卡片与批次原文。缺口检查在新形态下更像「这批素材里缺什么」，与「自动整理成策划」是同一个任务的两端。

### 先导版为四支柱留的门，且只留这些

先导 Epic 的 DEC-17 用「以后补贵不贵」判据留了四扇门，每扇都对应四支柱中的一项依赖：

| 留门 | 服务于 | 不留的代价 |
|---|---|---|
| (a) 卡片记录素材来源分类，默认最严格 | Agent 生成用途的授权前提 | 半年后无法让摄影师对几百张卡逐个回忆来源 |
| (b) 批量搬入保留原始整段文本与批次 ID | Agent 整理策划最有价值的上下文 | 聊天拆条后对话顺序永久丢失 |
| (c) 布局信息与卡片内容分离 | 画布只需新增坐标与边表 | 否则画布要改卡片写路径 |
| (d) 卡片由账号持有，空间归属经成员关系表达 | 资源库是账号级而非项目级 | 否则从项目级改账号级要迁移全部读写路径 |

画布渲染、节点连线、自由坐标、视频节点、model provider、检索索引、知识库表、通用 block 抽象一律不建。这些都是「新增而非重构」，现在做与以后做成本相同。

### 与旧 intelligence roadmap 的关系

旧 `creative-shoot-intelligence` roadmap 的三层知识形态（平台公共底座 + 摄影师私有增强 + 项目研究包）和「同一知识第 3 次跨项目复制才晋升」的判定仍然是知识库支柱的合理起点，不推翻。变化的只有两点：一是它的输入从旧 ShootPlan 换成资源库卡片；二是它的启动 gate 从旧 G1–G4 换成先导 Epic 的 `pilot-evidence-go` 与 `manual-curation-too-costly` disposition。旧 roadmap 保持只读，不进入实现。

## 当前倾向

- 四支柱是产品定位，不是架构承诺；每一项独立立项、独立验证，任何一项失败不连带其它。
- 建设顺序：**资源库（先导 pilot）→ 知识库 + Agent（输出落成候选卡片 / 候选拍摄项）→ 画布**。画布不在 Agent 之前立项。
- 内置知识库的 IP 暴露是 SaaS 定位下的真实约束，账号私有知识库应先于内置知识库；内置层只承载无争议的事实性文字描述，原作图片与设定集截图继续 display-only。
- Agent 的输出永远处于候选层：可追溯来源、可编辑、可拒绝、可撤销、无外部写权限。这条红线在先导 Epic 验收 16 已固化。
- 个人风格不单独建库，仍按旧 brainstorm 的判断由历史拍摄项统计得出。

## 已敲定的点

- **已拍板（2026-09-04）：远期形态为「资源库 + 知识库 + Agent 助手 + 画布节点」四支柱共同构成创作系统。** 灵感墙是资源库的第一形态；知识库在存储形状上与资源库同构。
- **已拍板（2026-09-04）：先导 pilot 验证的是资源层。** 「素材堆积但策展不发生」不判 stop，记为 `manual-curation-too-costly`，作为 Agent 方向的直接证据输入。
- **已拍板（2026-09-04）：卡片由账号持有。** 落为先导 Epic DEC-17 (d)；先导版仍约束一张卡同一时间只属于一个空间，跨空间能力留在证据门后。
- **已拍板（2026-09-04）：资源库与知识库不合表。** 只共享既有权利矩阵与媒体身份，不建通用资产抽象。
- **已拍板（2026-09-04）：画布不在 Agent 之前立项。** Agent 第一版由现有灵感墙与拍摄清单承接输出。
- 沿用旧 brainstorm 已拍板项：原作素材 display-only、生成只接受自有或授权素材、AI 先做检查后做生成、采用率为唯一先导指标、指标不外化、创作与计价解耦。

## 遗留问题 & 下一步

1. **`planningmedia` 的 holder 耦合**：矩阵判定与媒体身份可复用，但上传与绑定路径以旧 ShootPlan 为 holder。先导 ITEM-3 要为创作空间新增 holder 类型或独立资产生命周期；知识库与 Agent 立项时同样要复用这一层，不得各建一套权利模型。
2. **知识库的检索形态**：给 Agent 用的检索是向量、结构化字段还是两者混合，取决于 Agent 第一版的任务形态（整理 vs 检查），先导结束前不决定。
3. **画布的节点类型**：视频节点已明确与画布一并评估；是否需要「知识节点」（把知识库条目直接拉到画布上）待画布立项时讨论。
4. **内置知识库的运营模型**：旧 brainstorm 的「响应工单而非预建百科」仍是倾向，但需要在知识库立项时按 SaaS 多租户重新评估成本。
5. **Agent 与摄影师的协作边界**：owner 表述为「摄影师资深 + Agent 协作」，即 Agent 是副驾驶而非自治执行者；具体交互形态（对话式、批注式、还是节点图内联）在 Agent 立项时通过原型决定，不在本文预设。

### 下一步

等待先导 Epic 的 `pilot-evidence-go`。结果为 `go` 或 `manual-curation-too-costly` 时，以本文为定位输入，先评估「知识库 + Agent」是否立项；画布在 Agent 之后单独评估。结果为 `stop` 且属于「素材不堆积」形态时，本文降为 archived。
