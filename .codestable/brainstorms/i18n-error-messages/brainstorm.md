# 错误说明的多语言设计

> 创意空间 | 2026-10-10 创建 | 状态：暂缓，当前不做国际化；有外语摄影师需求时再启动

## 出发点

智能体工具的错误处理改成「原因交给模型」之后（`creativeops.Explain` / `Public`，见 `feat/creative-workspace-redesign` 分支 `ef70c7f`、`a10ca93`），画布、提示词等约 60 处校验都写了中文原因。如果以后支持多语言，这些中文说明该怎么处理？

## 现状（2026-10-10 核实）

- `PublicMessage()` 只被智能体消费：经 `asRefusal` / `editRefusal` 写进工具结果给模型看。HTTP 接口不返回这些原因，仍只给错误码。
- 前端按错误码映射文案（如 `frontend/src/creative-canvas/editor/agentState.ts`），尚未引入任何 i18n 框架。
- 智能体系统提示词（`backend/internal/creativeagent/context.go` 的 `assistantInstruction`）没有约定回复语言；工具失败规则写的是「有 message 就照实转述」。

结论：这些中文原因现在的读者只有模型，不是摄影师。

## 倾向方案：按读者分两路

1. **给模型的原因：单一语言，不建多语言目录。**
   模型读一种语言的原因，就能用摄影师的语言解释，翻译由模型完成。国际化启动时只需：
   - 把提示词规则改成「用摄影师的语言转述 message 的意思」；
   - 视情况把原因统一改写为英文（模型最稳、也不暗示界面只支持中文）。原因全部集中在 `Explain` / `refuseTool` 调用处，是一次性机械替换。
2. **给界面的错误：后端只出错误码加参数，文案在前端语言包。**
   现有错误码映射已是这个模式；接入 i18n 框架时把映射表搬进语言包即可，后端不动。底线：后端写的自然语言不直接上界面。
3. **唯一需要升级 `Explain` 的情形：** 要把具体原因直接显示在界面上（如编辑失败提示具体节点和尺寸范围）。届时改成消息键加结构化参数，例如 `Explain(err, "canvas.resize_bounds", map[string]any{"node": id, "min": 160, "max": 1200})`：HTTP 返回键和参数由前端套模板，给模型的那份由后端按默认语言渲染。所有原因走同一入口，迁移是机械的。

## 明确不做

- 不提前把约 60 处原因改成消息键并维护多语言目录：读者只有模型，模型自己会翻译，提前做是为不存在的需求付维护成本。

## 可随时顺手做的小事（未做）

- 在系统提示词加一句「用摄影师使用的语言回复，工具返回的 message 转述成同一种语言」。一行改动，外语摄影师出现时即生效。

## 启动信号

- 出现非中文摄影师，或产品决定面向海外（参见 SaaS 定位）；
- 或需要把工具失败的具体原因直接展示在界面上（触发第 3 条）。
