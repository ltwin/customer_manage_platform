# 摄影师私域客户经营系统

> 创意空间 | 2026-07-05 | 下一步：cs-roadmap
> 2026-07-06：已由 cs-roadmap 消费并拆解为 active roadmap（`.codestable/roadmap/photographer-private-crm/`）；本文档保留为需求讨论的原始记录，后续拍板以 roadmap 与 ADR 为准。

## 出发点

Owner 是摄影师，客户全部来自私域流量（微信、QQ、Telegram）。原始痛点四条：

1. 客户信息（姓名、社交账号、手机、生日）只存在于社媒好友关系里，无法维护，导致遗忘和流失
2. 约单记录无法与客户关联，客户画像 / 活跃度分析无从做起，定制服务无抓手
3. 档期管理只能用系统日历，无法关联客户和套系
4. 套系（定价策略、张数/时长/底片/精修参数、拍摄类型）只靠备忘录，难以管理

讨论中对问题的重新定义：**四个痛点是同一个病的四个症状——客户资产寄生在聊天软件里，聊天软件只给"联系人"不给"关系"**。要做的不是四个独立功能，而是把 人（客户）—钱（订单）—时间（档期）—货（套系）连成一张网。客户画像 / 活跃度（痛点 2）不是功能，是链路打通后自然长出的视图。

## 聊过的方向

PM 视角补充的、owner 原清单没有的维度（均已认可，纳入范围盘子，优先级见"当前倾向"）：

- **多平台身份合并**——同一客户在微信/QQ/TG 有多个账号，模型必须是"一个客户挂多个社交身份"，否则订单历史被拆散到多个假客户上，画像永远做不准。痛点 1 的隐藏前提。
- **订单是流程不是记录**——真实生命周期：咨询→报价→定金定档→拍摄→选片→精修→交付→尾款/返图授权。漏收尾款、修图拖期是原清单遗漏的真实痛点。
- **提醒引擎**——光存生日不解决"遗忘"，系统要主动找人：生日前 N 天、拍后回访、超期未复购流失预警。这是"档案柜"与"经营系统"的分水岭。
- **来源与转介绍链**——私域摄影增长大头是老客转介绍，记录"谁介绍了谁"才能识别超级节点客户。
- **偏好与禁忌档案**——定制服务的原料是软信息（风格偏好、修图禁忌、cos 偏好），需要结构化的家。
- **财务视角**——定金/尾款、单均价、每单成本、套系毛利。缺钱的维度，客户分析就是空转。（首版仅保留定金/尾款标记，分析后置）

## 当前倾向

第一版形状（"先治忘"路线）：

| 模块 | 厚度 | 首版内容 |
|---|---|---|
| 客户档案 | 厚 | 多平台身份、渐进录入、偏好/禁忌备注、来源/转介绍 |
| 提醒引擎 | 厚 | 生日、拍后回访、流失预警；触达 = Telegram Bot 推送 + Web dashboard 今日待办 |
| 档期 | 中 | 日历视图 + 关联客户和套系，10 秒答复"某天有没有档" |
| 订单 | 薄 | 一条记录 + 状态流转 + 定金/尾款两个布尔标记；不碰支付（收款继续走支付宝/微信） |
| 套系 | 薄 | 静态定义：拍摄类型、定价方式（按时间/按张）、张数/时长/底片/精修参数，供订单和档期引用 |

Web 首页即 dashboard：今日待办 + 待收尾款 + 流失预警 + 本月概览；TG Bot 每日推送是把人拉回面板的钩子。

## 已敲定的点

- **定位：自用起步，按可产品化预留**（owner 选 B）——数据模型第一天起带账号/租户维度，认证层可扩展；但首版不做注册开放、计费、运营后台。⚠️ 结构性决策，建议走 `cs-domain` 落 ADR。
- **形态：响应式 Web 应用，桌面体验优先**（owner 电脑为主）——移动端首版只做查档期/看客户/快速记备注的轻路径；不做小程序、不做原生 App。
- **首版主攻"治忘"**（owner 选 A 并修正）——客户档案 + 提醒引擎做厚，档期中等厚度保留，订单轻量化。
- **提醒触达 = TG Bot + dashboard 组合**（owner 确认 A+D）——应用内提醒不解决遗忘（"记得打开应用"会成为新的遗忘点），必须主动推送到天天看的地方。
- **30 秒录入原则（贯穿性设计约束）**——微信/QQ 无开放 API，客户信息注定手工录入；工具存亡取决于录入成本。新建客户只需昵称+平台，其余字段渐进补全；任何页面可一句话追加备注。
- **明确不做：在线选片/云盘交付**——那是另一个产品的体量（市面有奇迹秀等专门工具），系统只记"已选片/已交付"状态。
- **明确不做：支付**——收款走支付宝/微信，系统只记定金/尾款状态。

## 遗留问题 & 下一步

- **部署形态与数据隐私**：客户联系方式等 PII 放云上还是自托管？产品化预留倾向云部署，但敏感度需要 owner 拍板。
- **流失预警的 N 值**："超过 N 个月未约单"的阈值可能因拍摄类型而异（写真复购周期 ≠ cosplay），建议做成可配置而非写死。
- **粘贴聊天片段自动抽取信息**（生日/电话）——降低录入成本的增强项，后置，roadmap 排期时再评估。
- **客户画像 / 活跃度分析**：数据链路通了之后的二期视图，首版不做，但数据模型设计时要保证订单-客户-套系关联完整，别堵死。
- **技术选型**（框架、数据库、TG Bot 接入方式）：本轮未讨论，留给 roadmap 架构层详设 / design。
