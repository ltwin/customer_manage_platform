# 数据模型自首版起携带账号维度（自用起步、预留产品化）

## Context

项目定位在 2026-07-05 脑暴中敲定（见 `.codestable/brainstorms/photographer-private-crm/brainstorm.md`）：自用起步，但保留将来给同行摄影师使用的产品化可能。

矛盾在于：首版只有 owner 一个人用，最省事的做法是纯单用户 schema；但如果将来产品化，"数据归属于哪个账号"这一维度是后补代价最高的一类改动——涉及全部业务表加列迁移、所有查询改写加过滤、权限层从无到有重构，且极易在遗漏处造成跨账号串数据。

## Decision

所有业务数据（客户、社交身份、订单、档期、套系、提醒、转介绍关系）自首版起携带账号归属维度（`account_id` 或等价外键）；认证层做成可扩展抽象（首版可以是写死的单账号登录，但接口上不假设"全系统只有一个使用者"）。

首版仅单账号运行：不做注册开放、不做计费、不做运营后台。

## Consequences

- 正面：产品化时无需数据迁移，开多账号只是放开注册；查询天然按账号隔离，多账号阶段不会串数据。
- 负面：首版每张表多一个归属列、每个查询多一个过滤条件，单账号阶段看似冗余；需要约定一个默认账号的初始化方式。
- 新增约束：**任何新业务表必须带账号归属；任何查询必须限定账号范围**。这条约束应进入后续 design / code review 的检查口径。

## Alternatives Considered

- **纯单用户 schema**：首版最简，但产品化时需全库迁移 + 全量代码改写，代价不可控且易出串数据事故。否决。
- **首版即完整 SaaS**（注册、计费、数据隔离、运营后台全做）：自用价值尚未验证就为想象中的用户做功能，过度工程，直接拖垮首版工期。否决。
